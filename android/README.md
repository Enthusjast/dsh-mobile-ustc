# Android development

The Android tree now builds a Compose/Hilt development APK. `:core:protocol` owns strict JSON/JCS and approval contracts; `:core:crypto` owns ES256, DPoP and device-registration proof preparation; `:core:auth` owns PKCE, Discovery and independent JWT verification; `:core:network` owns bounded authenticated HTTPS. `:core:keystore` owns platform keys/per-use biometric operations, `:core:ui` owns the Material theme and `:app` wires browser login, device enrollment and the authorized runtime directory. Real school identity, WSS/session UI, durable account/cache recovery and the remaining foreground workflows are not complete. See [login architecture and its boundaries](../docs/android-authentication.md).

Run from this directory with JDK 17 or 21, Android SDK Platform 36 and Build Tools 35.0.0:

```sh
./gradlew check :app:assembleDebug
```

Or run `npm run test:android` from the repository root for JVM tests and Android lint. Set `sdk.dir` in your ignored `local.properties`, or configure `ANDROID_HOME`. `./gradlew -PjvmOnly=true check` / `npm run test:android:core` runs all four shared JVM modules without an Android SDK. Kotlin is pinned to 2.3.21, AGP to 8.13.2, Hilt to 2.58, Compose BOM to 2025.10.01 and the Gradle wrapper to 8.14.5 with the published distribution SHA-256. The application has minSdk 26 and target/compileSdk 36; distribution policy and release signing remain gates. Dependencies use Maven Central/Google and exact versions; generated lockfiles and SHA-256 verification metadata are committed. Verification metadata records the initial downloads; it is not a claim that an independent signature or vulnerability review was completed. Update locks/checksums deliberately when changing dependencies. Compatibility references: [Kotlin Gradle](https://kotlinlang.org/docs/gradle-configure-project.html), [AGP 8.13](https://developer.android.com/build/releases/past-releases/agp-8-13-0-release-notes).

The default APK at `app/build/outputs/apk/debug/app-debug.apk` disables login without school configuration. Build with `-PdeploymentConfig=/absolute/path/to/verified-public-deployment.json` to supply the exact registered issuer/client/resource/remote service; use `../deploy/android/deployment.example.json` only as a template. Configuration is validated with the same strict public schema before packaging. Unknown fields such as client secrets are rejected; an unconfigured build removes an earlier generated configuration. There is no embedded fallback IdP or model credential. Browser state, verifier, codes and tokens remain in memory and process death requires reauthentication.

The shared modules also provide [encrypted account checkpoints and verified token refresh](../docs/android-account-recovery.md): platform AES-GCM storage, signed cached-access validation, optional refresh ID tokens, issuer-key rotation and explicit uncertain-rotation markers. This foundation passed JVM/HTTPS and separate platform vault tests; the application's account controller has not been connected to it yet. The current APK still has the in-memory account lifecycle described above.

`JsonDocument` uses Jackson Core 2.20.1 for a strict UTF-8, duplicate-name and syntax preflight, then the erdtman JCS 1.1 implementation for ECMAScript number formatting and UTF-16 property ordering. The JCS library's parser alone accepts some duplicate-null names and nonstandard number forms, so it is never the validation boundary. Both parsed and generated objects enforce 128 KiB, 32 levels, 16,384 nodes and scalar Unicode. Parsed object/array containers are copied and immutable. Errors omit input text and parser causes.

Approval contexts require every exact field, enrolled identifiers, current millisecond UTC times, unique resource facts and canonical 32-byte nonces. The binding includes full arguments and resources. Decisions allow only `allow_once` or `reject`; both bind all execution/identity/policy/nonce facts, have at most the request's expiry and use the same 30-second issue freshness and five-second future clock limit as Go/TypeScript. No signing API accepts a caller-provided binding hash in place of the context.

Crypto uses Nimbus JOSE+JWT 10.5 for ES256 verification and DER/JOSE conversion. The registered key is independently supplied; embedded private material, caller keys, remote key URLs, unknown/aliased fields, wrong purpose and noncanonical JOSE/JSON bytes are rejected. `ApprovalSignatures.prepare` creates complete immutable signing bytes before a platform prompt. `PreparedApprovalSignature.finishDerSignature` converts a JCA `SHA256withECDSA` DER result to the 64-byte JOSE form, independently verifies it and rechecks expiry. Cancellation or one completion ends that operation. These objects are ephemeral and must not be restored across process death or authority changes. This is content signing, not a replacement for current server authorization or the host's one-use execution journal.

Tests consume the same `contracts/security/jcs-vectors.json` and `approval-signatures.json` as Go/TypeScript. `approval-kotlin-signatures.json` adds public-only Kotlin/JCA allow, reject, altered-choice and raw-DER vectors; all three languages verify those vectors. Regenerate deliberately:

```sh
./gradlew :core:crypto:generateInteropVectors
```

Fresh private keys exist only in the generator's process memory. Regeneration changes public keys/signatures and writes the public fixture; it does not modify schema or lease fixtures. Rerun `./gradlew check`, `npm run verify` and `go test -race -count=1 ./...` in `services/remote` after changing shared vectors. Go test caching must be disabled because the fixtures live outside its module.

`DeviceKeyStore` creates non-exportable P-256 AndroidKeyStore keys with separate proof/approval aliases and explicit versions. Scope IDs represent the account/organization mapping owned by the authenticated account lifecycle; validating their UUID syntax is not authorization. Proof signing requires the proof-key handle and no user authentication. Approval enrollment requires a secure device lock and enrolled strong biometrics. Approval keys require authentication for every use and are invalidated by biometric enrollment changes. API 26–29 use the per-operation validity setting; API 30+ use explicit `AUTH_BIOMETRIC_STRONG`. This adapter supports strong-biometric approval; it does not silently fall back to a device PIN or an unprotected key. The [Android biometric documentation](https://developer.android.com/identity/sign-in/biometric-auth) explains these platform constraints.

`beginApproval` binds the prepared signature to the platform key thumbprint and returns a `BiometricPrompt.CryptoObject`. The successful callback must return the same Signature instance before `finish` can produce a proof. Expiry is rechecked after signing. Cancellation, key deletion or account-owner disposal fences old operations/handles; reinitializing a cancelled Signature stops a retained CryptoObject from signing. One handle retains at most one approval operation, and one store retains at most 64 open handles. Closing a store fences its handles while preserving enrolled platform keys; deleting a key removes its explicit alias/version. Missing or invalidated keys require explicit re-enrollment and are never silently replaced. Device revocation, OIDC logout, account/cache cleanup and closing the visible prompt must still be connected by the application lifecycle.

An explicit `requireHardware` policy checks KeyInfo hardware protection and, for approval keys, hardware enforcement of authentication. Failure denies creation/use. This local check is not remote attestation, and does not establish a production school's hardware policy. StrongBox-specific requirements, attestation verification and physical-device behavior remain separate gates.

For an explicitly selected test device/emulator:

```sh
ANDROID_SERIAL=<test-serial> ./gradlew :core:keystore:connectedDebugAndroidTest
```

Three noninteractive platform tests verify persistent non-exportable keys, distinct scopes, JOSE-encoded ECDSA signatures, deletion/disposal and approval gating. They do not configure a device PIN or enroll biometrics. Two interactive tests open actual authentication UI only with `-PbiometricFixture=true`; provision a dedicated test fingerprint and confirm the allow/reject/device-registration prompts. On an owned emulator, its fingerprint sensor controls can supply the test samples. Do not inject test samples into another device or unrelated prompts. The test activity and shared public fixtures exist only in the test APK, not the published library. See [platform test evidence](../docs/android-keystore.md).

Still required: verified school PKCE/DPoP configuration, accepted-device recovery and encrypted token persistence/refresh, WSS leases/reconnect, full-context tool-approval review, account/runtime-isolated encrypted caching, sessions/chat/questions, files/push and full device/process/network tests. The development APK and fixture tests do not establish physical hardware policy, real school identity, all foreground workflows, M1 or M2 acceptance.
