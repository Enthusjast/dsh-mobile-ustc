# Android development

The Android tree builds a Compose/Hilt development APK. `:core:protocol` owns strict JSON/JCS and approval contracts; `:core:crypto` owns ES256, DPoP and device-registration proof preparation; `:core:auth` owns PKCE, Discovery, independent JWT verification and public binding facts; `:core:session` owns bounded display/history/assistant merging; `:core:network` owns authenticated HTTPS/WSS and foreground read/binding/command/creation flows. `:core:command` owns immutable intents and delivery facts; `:core:data` owns the Room/SQLCipher encrypted command journal and confirmed transcript cache. `:core:keystore` owns platform keys/per-use biometric operations, `:core:ui` owns the Material theme and `:app` wires the frontend. School identity acceptance, offline-policy/device acceptance and the remaining interactive workflows remain gates. See [login architecture and its boundaries](../docs/android-authentication.md).

Run from this directory with JDK 17 or 21, Android SDK Platform 36 and Build Tools 35.0.0:

```sh
./gradlew check :app:assembleDebug
```

Or run `npm run test:android` from the repository root for JVM tests and Android lint. Set `sdk.dir` in your ignored `local.properties`, or configure `ANDROID_HOME`. `./gradlew -PjvmOnly=true check` / `npm run test:android:core` runs the six shared JVM modules without an Android SDK. Kotlin is pinned to 2.3.21, AGP to 8.13.2, Hilt to 2.58, Compose BOM to 2025.10.01 and the Gradle wrapper to 8.14.5 with the published distribution SHA-256. The application has minSdk 26 and target/compileSdk 36; distribution policy and release signing remain gates. Dependencies use Maven Central/Google and exact versions; generated lockfiles and SHA-256 verification metadata are committed. Verification metadata records the initial downloads; it is not a claim that an independent signature or vulnerability review was completed. Update locks/checksums deliberately when changing dependencies. Compatibility references: [Kotlin Gradle](https://kotlinlang.org/docs/gradle-configure-project.html), [AGP 8.13](https://developer.android.com/build/releases/past-releases/agp-8-13-0-release-notes).

The default APK at `app/build/outputs/apk/debug/app-debug.apk` disables login without school configuration. Build with `-PdeploymentConfig=/absolute/path/to/verified-public-deployment.json` to supply the exact registered issuer/client/resource/remote service; use `../deploy/android/deployment.example.json` only as a template. Configuration is validated with the same strict public schema before packaging. Unknown fields such as client secrets are rejected; an unconfigured build removes an earlier generated configuration. There is no embedded fallback IdP or model credential. Pending browser state/verifier/code remain in memory. Completed account credentials and enrollment checkpoints use the independent encrypted vault; a pending browser flow still requires a new login after process death.

The optional [notification flow](../docs/android-notifications.md) uses explicitly configured Firebase Messaging 26.0.1/FID enrollment, a separate encrypted routing vault, generic account-fenced notifications and authenticated current-state reads. Approval references open an unsigned review; ordinary/timed question references select a matching fresh native form without claiming or answering it. Supply `-PpushConfig=/absolute/path/to/public-push.json` together with the matching deployment configuration. The default APK does not initialize Firebase or register a push channel. Google delivery, OEM adapters and target-device background acceptance remain gates.

Notifications resolve a [known session](../docs/known-session-access.md) through its exact authenticated resource, independently of host/session enumeration. The temporary resource context is revalidated on foreground and credential refresh. Question answers use their own narrow, original-device status route when generic `command.status` is absent; other command requirements remain unchanged. Returning from this view clears the context and opens reminders.

The shared SDK can now read and strictly validate [APK release metadata](../docs/app-release-metadata.md), including the requested current version, package, client support window, protocol/Android compatibility and independently supplied HTTPS download origins. This has no application UI or automatic check yet; private downloads, actual APK signature verification and system installation/recovery remain pending.

The shared modules also provide [encrypted account checkpoints and verified token refresh](../docs/android-account-recovery.md): platform AES-GCM storage, signed cached-access validation, optional refresh ID tokens, issuer-key rotation and explicit uncertain-rotation markers. The application controller now uses this store for device restoration, authoritative revalidation, foreground renewal and explicit reauthentication after uncertain rotation. Pending-key cleanup preserves the verified current account, and local exit fences old callbacks before destroying credentials/keys. JVM, HTTPS and platform/controller evidence is separated from the remaining real-school and OS process-death gates in that document.

The [foreground session reader](../docs/android-realtime.md) now opens authorized runtime/session directories and displays snapshots, paged history and live assistant content over TLS. It owns heartbeat, fresh-ticket reconnect and account/foreground cleanup, with a bounded confirmed-history window and an [encrypted persistent transcript cache](../docs/android-transcript-cache.md). Fresh resource authority is required before loading disk history, including while the host is offline. The [encrypted outbox and foreground composer](../docs/android-command-delivery.md) support queue/steer text, status reconciliation, explicit same-ID retry and epoch-bound interruption. The [ordinary and timed question forms](../docs/android-questions.md) share the current read socket and encrypted answer coordinator. The [signed-approval view](../docs/android-approvals.md) enables current owner authority, complete paged action review, per-use strong biometrics and original-proof HTTPS admission on that socket. School identity continues to use local fixtures until configuration is ready.

The [phone host-binding flow](../docs/android-host-binding.md) now reviews the installation fingerprint, requires explicit confirmation and waits for independent host confirmation plus a current directory grant. It retires codes on background/account changes and reconciles uncertain results with reads. The host-side production UI/key provider and real-school acceptance remain gates.

`JsonDocument` uses Jackson Core 2.20.1 for a strict UTF-8, duplicate-name and syntax preflight, then the erdtman JCS 1.1 implementation for ECMAScript number formatting and UTF-16 property ordering. The JCS library's parser alone accepts some duplicate-null names and nonstandard number forms, so it is never the validation boundary. Both parsed and generated objects enforce 128 KiB, 32 levels, 16,384 nodes and scalar Unicode. Parsed object/array containers are copied and immutable. Errors omit input text and parser causes.

Approval contexts require every exact field, enrolled identifiers, current millisecond UTC times, unique resource facts and canonical 32-byte nonces. The binding includes full arguments and resources. Decisions allow only `allow_once` or `reject`; both bind all execution/identity/policy/nonce facts, have at most the request's expiry and use the same 30-second issue freshness and five-second future clock limit as Go/TypeScript. No signing API accepts a caller-provided binding hash in place of the context.

Crypto uses Nimbus JOSE+JWT 10.5 for ES256 verification and DER/JOSE conversion. The registered key is independently supplied; embedded private material, caller keys, remote key URLs, unknown/aliased fields, wrong purpose and noncanonical JOSE/JSON bytes are rejected. `ApprovalSignatures.prepare` creates complete immutable signing bytes before a platform prompt. `PreparedApprovalSignature.finishDerSignature` converts a JCA `SHA256withECDSA` DER result to the 64-byte JOSE form, independently verifies it and rechecks expiry. Cancellation or one completion ends that operation. These objects are ephemeral and must not be restored across process death or authority changes. This is content signing, not a replacement for current server authorization or the host's one-use execution journal.

Tests consume the same `contracts/security/jcs-vectors.json` and `approval-signatures.json` as Go/TypeScript. `approval-kotlin-signatures.json` adds public-only Kotlin/JCA allow, reject, altered-choice and raw-DER vectors; all three languages verify those vectors. Regenerate deliberately:

```sh
./gradlew :core:crypto:generateInteropVectors
```

Fresh private keys exist only in the generator's process memory. Regeneration changes public keys/signatures and writes the public fixture; it does not modify schema or lease fixtures. Rerun `./gradlew check`, `npm run verify` and `go test -race -count=1 ./...` in `services/remote` after changing shared vectors. Go test caching must be disabled because the fixtures live outside its module.

`DeviceKeyStore` creates non-exportable P-256 AndroidKeyStore keys with separate proof/approval aliases and explicit versions. Scope IDs represent the account/organization mapping owned by the authenticated account lifecycle; validating their UUID syntax is not authorization. Proof signing requires the proof-key handle and no user authentication. Approval enrollment requires a secure device lock and enrolled strong biometrics. Approval keys require authentication for every use and are invalidated by biometric enrollment changes. API 26–29 use the per-operation validity setting; API 30+ use explicit `AUTH_BIOMETRIC_STRONG`. This adapter supports strong-biometric approval; it does not silently fall back to a device PIN or an unprotected key. The [Android biometric documentation](https://developer.android.com/identity/sign-in/biometric-auth) explains these platform constraints.

`beginApproval` binds the prepared signature to the platform key thumbprint and returns a `BiometricPrompt.CryptoObject`. The successful callback must return the same Signature instance before `finish` can produce a proof. Expiry is rechecked after signing. Cancellation, key deletion or account-owner disposal fences old operations/handles; reinitializing a cancelled Signature stops a retained CryptoObject from signing. One handle retains at most one approval operation, and one store retains at most 64 open handles. Closing a store fences its handles while preserving enrolled platform keys; deleting a key removes its explicit alias/version. Missing or invalidated keys require explicit re-enrollment and are never silently replaced. The application now binds these operations to current foreground, navigation, account and review generations. Local exit, server device revocation and IdP logout retain their distinct semantics; physical biometric/credential-change and hardware-policy acceptance remain gates.

An explicit `requireHardware` policy checks KeyInfo hardware protection and, for approval keys, hardware enforcement of authentication. Failure denies creation/use. This local check is not remote attestation, and does not establish a production school's hardware policy. StrongBox-specific requirements, attestation verification and physical-device behavior remain separate gates.

For an explicitly selected test device/emulator:

```sh
ANDROID_SERIAL=<test-serial> ./gradlew :core:keystore:connectedDebugAndroidTest
```

Three noninteractive platform tests verify persistent non-exportable keys, distinct scopes, JOSE-encoded ECDSA signatures, deletion/disposal and approval gating. They do not configure a device PIN or enroll biometrics. Two interactive tests open actual authentication UI only with `-PbiometricFixture=true`; provision a dedicated test fingerprint and confirm the allow/reject/device-registration prompts. On an owned emulator, its fingerprint sensor controls can supply the test samples. Do not inject test samples into another device or unrelated prompts. The test activity and shared public fixtures exist only in the test APK, not the published library. See [platform test evidence](../docs/android-keystore.md).

The [explicit owned-emulator APK/Go/DSH composition](../docs/android-device-composition.md) now completes actual native-key registration, scoped chat, biometric allow/reject, real Bash effects/results, native archive/restore, scanned uploads, bounded export/document saves and encrypted controller recreation. Run it separately with `npm run test:remote-android -- emulator-5594` after provisioning the dedicated unlocked AVD and test fingerprint.

Still required: verified school PKCE/DPoP configuration, production host confirmation/key provisioning, offline-policy and physical-device acceptance, real file storage/scanner infrastructure, large-file tests, real background delivery, APK updates and full device/process/network tests. The [shared approval transport, transient reviews and encrypted decision records](../docs/android-approvals.md) validate exact online contexts, prevent stale review reuse and retain original proofs in the versioned SQLCipher/Room store. Encrypted account checkpoints, accepted-device recovery, verified credential rotation and foreground read reconnection have fixture coverage. The development APK and fixture tests do not establish physical hardware policy, real school identity, all foreground workflows, M1 or M2 acceptance.

The [foreground creation view](../docs/android-session-creation.md) uses current host-advertised workspace/preset choices, an epoch-bound original intent and separately persisted result UUID. Room version 3 migrates existing commands and encrypted history without destructive reset. Unknown attempts are reconciled without automatic replay; opening a settled result revalidates the session directory and current read scope.
