# M1 Resource authentication foundation

This is an implementation baseline, not evidence that the school identity provider has enabled the remote-control client or resource.

## Implemented

`services/remote/internal/auth` verifies OAuth JWT access tokens against a configured JWKS URL. It pins the issuer, audience, OAuth client allowlist, required scopes and acceptable algorithms; requires `at+jwt`, `iss`, `sub`, `client_id`, `jti`, `iat`, `exp`, and DPoP key binding; rejects duplicate JSON claims and refuses caller-supplied key URLs. Supported access-token signatures are RS256 and ES256; proof keys are P-256.

JWKS responses must also be valid UTF-8 JSON without duplicate members at any depth. Public-key parsing rejects private RSA/EC/symmetric key fields even when their value is null, as well as remote key references. A malformed refresh fails without replacing previously cached keys; an expired cache still cannot be used as a fallback. Component tests exercise these boundaries with a local JWKS server.

The shared strict JSON decoder rejects invalid UTF-8 and unpaired UTF-16 escapes before Go can replace them. Identity claims, public requests and protected configuration therefore retain the exact decoded strings; valid surrogate pairs and escaped literal backslashes remain supported.

The middleware requires the DPoP authorization scheme, checks the proof signature, `typ`, method, externally configured URI, access-token hash (`ath`), proof-key thumbprint, timestamp, server nonce and one-use `jti`. It returns a fresh nonce after an authenticated request. Public URL comparison uses only configured origin and request path; `Forwarded` and `X-Forwarded-*` headers are not trusted.

`POST /v1/devices` requires an approval-key ES256 JWS with type `dsh-device-registration-proof+jwt`. Its claims bind `iss`, `sub`, `aud=urn:dsh-mobile-ustc:device-registration`, `iat`, unique `jti`, `approval_key_jkt`, `proof_key_jkt`, `device_name_sha256`, and the current DPoP `dpop_jti`. The name digest is unpadded base64url of SHA-256 over the trimmed UTF-8 name. Replaying the JWS with a different request fails because the DPoP proof JTI must match and is consumed once. Exact retries using fresh proofs return the original active device; [current-key enrollment reconciliation](device-enrollment-recovery.md) defines the status read, conflict/revocation rules and foreground Android recovery boundaries.

The `GET /v1/me` route returns verified principal claims and authoritative service user/organization mapping for a provisioned active account. `GET /healthz` is liveness-only; `GET /readyz` pings PostgreSQL. Device registration binds its proof key to the current DPoP key, requires a distinct approval key, and verifies an ES256 proof of possession bound to the verified identity, both keys, device name, and current DPoP proof. Every directory, command-status, grant, ticket-issue, and revocation request checks that the DPoP key belongs to a non-revoked device. Owners can delegate only action and resource scopes contained in their own active grant; an owner scope must include `grant.manage`. Organization admins can manage grants across their organization and assign owner grants. Grant changes increment the grant version and commit audit and outbox events atomically. Host/runtime/session/command-status queries filter active grants and explicit action, workspace, and session scopes in PostgreSQL. Realtime ticket issuance binds a random 30-second ticket to one device key version, runtime, grant version, and explicit scope; PostgreSQL stores its SHA-256 digest, and the internal store consumes it atomically after rechecking current access. `GET /v1/realtime` validates mobile tickets or host credentials, sends a fresh 256-bit challenge, and consumes mobile tickets only after an ES256 proof from the registered key succeeds. Host runtime metadata and connection ID are stored; the connection ID prevents an older socket from refreshing or detaching a newer connection. Device WSS leases end within five minutes, and host leases end with the host credential. The WSS handler routes text-only queue/steer submissions and epoch-bound cancellation to the current host runtime, persists command metadata/digests, and accepts host receipt transitions. It rechecks the current device and grant on every command, including the separate `session.cancel` action. [Cancellation notes](session-cancel-protocol.md) describe durable retry and native turn-end semantics. Session snapshots, fixed-cursor history pages and assistant streams now use connection-scoped subscriptions and explicit `session.read` permission. The Relay rechecks current device/grant/resource scope and host ownership before each content frame. The production entrypoint now propagates revocations through a transactional outbox and independent periodic batch checks; [revocation notes](revocation-propagation.md) describe targeting, failure behavior and the single-process deployment limit. [Blocking question snapshots and answers](question-protocol.md) are implemented with separate read/answer permissions, scoped one-use consumption and durable command receipts. [Timed-question transport](timed-question-protocol.md) also binds UI claims to a current socket/subscription and requires read plus answer authority. Native continued replies pass a session checkpoint before agent_queued. Signed tool approvals are now available through the explicitly configured policy and paired-proof transport; mobile grant-lease renewal remains open. See [approval transport](approval-protocol.md). The server bounds request and idle time and shuts down gracefully.

Host enrollment endpoints create a pending host, installation, runtime, and opaque workspace records. The host OAuth client must be separately listed in `REMOTE_HOST_CLIENT_IDS`; its DPoP key must match the registered installation public key. An active organization member confirms from a registered phone device, and the host client confirms with the installation key. Only after both confirmations does the service activate the profile and create owner grants for the host owner and confirming user. Codes are 256-bit URL-safe values stored only as SHA-256 digests. The [phone binding flow](android-host-binding.md) previews display metadata with an unexpired code in the request body, checks the full installation fingerprint and reconciles current-actor status without automatically replaying a write. Ordinary status reads are restricted to participants; host reads are key-bound. Host OAuth clients cannot use phone enrollment/protected routes. Shared active hosts/installations do not activate a pending sibling profile, and one profile's expiry does not revoke its siblings. Apply 008 for the enrollment eligibility index. The production host-local user confirmation UI remains a gate, and migration 002 requires reconciliation if enrollment rows already exist.

After activation, the installation owner can request a one-use 90-second challenge and exchange an installation-key ES256 proof for an opaque five-minute connection credential. Challenge issuance is limited to four pending and 20 per five minutes; no more than eight unexpired credentials can be active per installation. Challenge and credential digests are stored, challenge consumption and credential creation are atomic, and validation checks active host state, key version, expiry, and the registered thumbprint. The `REMOTE_HOST_CLIENT_IDS` allowlist also gates both new routes. The Relay validates the host credential, requires a fresh signed key challenge, and limits the host connection to credential expiry. The host plugin now has a reconnecting WSS adapter: it verifies the handshake challenge with a provider-supplied signer, publishes metadata-only session catalog snapshots and deltas, accepts digest-matching text submissions, writes through the current DSH session controller and encrypted command journal, returns durable command receipts, and serves projected session snapshot/history/assistant frames through the same current-process controller. The [Host REST credential provider](host-credential-provider.md) now exchanges one-use challenges through a verified resource-session adapter and the enrolled signer, with bounded caching, purpose checks and account-lifetime fencing. Enrollment/reenrollment, the actual school login/refresh adapter and a production OS key store remain integration work.

The host plugin writes mutating commands to a profile-local SQLite WAL journal before dispatch, stores command/result bodies with AES-256-GCM, and only reports the `agent_queued` state after DSH session flush succeeds. Session creation also waits for its persistence checkpoint. A DSH `requestId` retry recovers a message that may have crossed the DSH boundary before a crash; other ambiguous mutations become `outcome_unknown`. Local IPC continues to use a local principal. The WSS path partitions the same journal by verified user/device identity. The DSH CLI 0.2.1-rc.2 test drives a command through a loopback WSS peer and the same live DSH Agent; it does not exercise the Go service or a production credential provider.

## Verification and remaining M1 work

`go test -race ./...` uses generated RSA and P-256 keys plus a local JWKS test server. Coverage includes issuer, audience, client, scope, expiration, not-before, `cnf.jkt`, JWT type, algorithm, duplicate JSON keys, DPoP method, URI, token hash, public device-key validation, approval-key proof of possession, host installation proof binding, private JWK rejection, initial nonce challenge, nonce retry, concurrent replay and proof reuse. The PostgreSQL integration test applies migrations 001 through 005 and covers challenge consumption, stored digests, key-bound ticket redemption, host credential validation, runtime connection replacement, command ID idempotency/conflict, receipt transitions, and status reads when `REMOTE_TEST_DATABASE_URL` is configured. Migrations 001–005 and this suite passed against an isolated PostgreSQL 18.6 cluster over a private Unix socket, including session catalog snapshots/deltas and scoped directory reads. The existing system cluster was not modified. This repository test establishes database behavior; combined Go/DSH evidence is recorded separately below. Neither establishes production deployment. `npm run verify` includes SQLite journal encryption/reopen/failure checks, the WSS JSON Schema golden-frame test, and the DSH 0.2.1-rc.2 CLI integration using local fixtures. HTTP and WebSocket tests verify readiness behavior, anonymous denial, host-client restrictions, both key-proof handshakes, message routing, idempotent retry/conflict, receipt delivery, drain, heartbeat limits, and strict request JSON. No live identity provider, token endpoint, Android client or production TLS ingress is involved.

Configuration still needs the organization’s actual issuer, resource audience, Android public-client ID, host-client ID, `REMOTE_HOST_CLIENT_IDS` allowlist and allowed scopes. The provider must issue access tokens with the configured audience, acceptable `at+jwt` signing, and DPoP key binding. This must be confirmed against the provider rather than relaxed in code.

Before M1 can pass its exit gate, remaining work includes verified school Authorization Code + PKCE/DPoP mobile integration, user/org provisioning, production PostgreSQL schema rollout, a shared multi-node replay store, connecting enrollment to an explicit local desktop confirmation UI, Android session merge/cache, header/projection baselines and large-record adaptation, signed tool approval and Android timed-question UI, mobile grant-lease renewal, durable multi-node revoke fanout and target-load/failure-window measurements, file-transfer controls, wrapping the local journal key with platform secure storage, a production host credential / OS key-store provider, command reconciliation after reconnect, and failure testing against the Go service.

The [approval signature foundation](approval-signatures.md) pins JCS/JOSE implementations and shares binding schemas plus Go/TypeScript signing/verification vectors. The [host journal](approval-journal.md) now commits one-use decisions, fences restart/takeover and exposes synchronous guard consumption; a native DSH test adapter verifies execution/denial boundaries. Current-authority/assurance enforcement, normal native callback/body/guard wiring and server transport/audit now have Go/PostgreSQL/real DSH fixture evidence. Production identity/key provisioning, Android full-context review and remaining capability/platform coverage still keep the complete signed-approval delivery gate open.

The verifier follows [RFC 9068](https://www.rfc-editor.org/rfc/rfc9068.html) for JWT access tokens, [RFC 8725](https://www.rfc-editor.org/rfc/rfc8725.html) for algorithm and token-type checks, [RFC 9449](https://www.rfc-editor.org/rfc/rfc9449.html) for DPoP proof binding, and [RFC 7638](https://www.rfc-editor.org/rfc/rfc7638.html) for JWK thumbprints.

The [session read protocol](session-read-protocol.md) records subscription/sync correlation, bounded fragments, scope revalidation and component-test evidence. The DSH CLI suite validates emitted WSS content frames against the shared JSON Schema; Go tests separately cover connection isolation, unsubscribe/replacement and authorization denial. These component tests do not replace the full Go/DSH/Android integration gate.

Command receipt delivery also rechecks each receiving socket's ticket against the actual command/session/workspace target. Same-device sockets can have different scopes; a valid broader runtime grant does not authorize cross-scope fanout. Out-of-scope receipts are skipped while the socket remains usable. Revoked leases or unavailable authority close the connection. Creation receipts additionally require negotiated creation support and the original workspace scope.

The separate `npm run test:remote-dsh` integration now passes against the Go production entrypoint, isolated PostgreSQL and npm DSH 0.2.1-rc.2. It exercises signed HTTP/device/host proofs and the actual catalog/command/session routes, including workspace-scoped session creation, grant revocation and a database dump that excludes session bodies and raw credentials. Its [evidence record](go-dsh-integration.md) distinguishes the locally signed identity/model fixtures from the remaining school IdP, Android and production key-provider gates.

The [Android development client](android-authentication.md) now implements S256 login preparation, AppAuth browser requests, strict OIDC/access-token verification, separated DPoP nonce handling, biometric registration proofs and a Compose/Hilt entrypoint. JVM HTTPS fixtures and Android UI/provider tests are component evidence; they do not establish school-client registration or a complete Go/DSH/Android login/session chain. Encrypted account/token storage, verified refresh and accepted-device reconciliation are now connected to the Android controller. Binding, WSS/session workflows, OS process-death/target-device acceptance and service-side account/device cleanup remain open; see the [account lifecycle evidence](android-account-recovery.md).

`GET /v1/me` now resolves the verified `(issuer, subject)` to the active service `user_id` and current `memberships` in one PostgreSQL statement. Missing, suspended and deleted users are denied; an active user without memberships receives an empty array. The route is available before device enrollment and never creates users, memberships or grants. Its response retains the verified issuer, subject, client and scopes. Android requires a valid internal UUID, exact identity/scope agreement, unique known membership roles and membership in the configured organization before preparing enrollment; changed internal mappings or lost membership end the local session. This snapshot is account context, not a runtime grant: every resource action still needs current service authorization. Never derive an internal UUID from an email or OIDC subject, or treat public deployment configuration as membership authority.

The production [shared DPoP repository](shared-dpop-state.md) now atomically consumes nonce/jti and rotates the next nonce in PostgreSQL, with cross-process/restart and unavailable-store tests. This closes the process-local replay prerequisite only; real-school identity, routing, durable control fanout and full milestone acceptance remain separate.

[Per-node control consumption](control-fanout.md) now has independent acknowledgements, commit-visible snapshot coverage, generation fencing and two-production-process revoke/restart evidence. Cross-node content/command routing now has [private node transport and owner HTTP routing](relay-routing.md) evidence; cluster workload/failure gates remain unfinished.

phone entering another node to the Host owner over mutual TLS. Approval HTTP,
Host file downloads and file-status requests also resolve that owner. Routing
inspection never consumes or substitutes for the original DPoP/file proof;
normal owner admission still runs once. Actual two-process npm DSH and separate
two-instance native-file/revoke fixtures passed; see the routing record for

inferred from these local tests.
