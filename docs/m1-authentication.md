# M1 Resource authentication foundation

This is an implementation baseline, not evidence that the school identity provider has enabled the remote-control client or resource.

## Implemented

`services/remote/internal/auth` verifies OAuth JWT access tokens against a configured JWKS URL. It pins the issuer, audience, OAuth client allowlist, required scopes and acceptable algorithms; requires `at+jwt`, `iss`, `sub`, `client_id`, `jti`, `iat`, `exp`, and DPoP key binding; rejects duplicate JSON claims and refuses caller-supplied key URLs. Supported access-token signatures are RS256 and ES256; proof keys are P-256.

The middleware requires the DPoP authorization scheme, checks the proof signature, `typ`, method, externally configured URI, access-token hash (`ath`), proof-key thumbprint, timestamp, server nonce and one-use `jti`. It returns a fresh nonce after an authenticated request. Public URL comparison uses only configured origin and request path; `Forwarded` and `X-Forwarded-*` headers are not trusted.

`POST /v1/devices` requires an approval-key ES256 JWS with type `dsh-device-registration-proof+jwt`. Its claims bind `iss`, `sub`, `aud=urn:dsh-mobile-ustc:device-registration`, `iat`, unique `jti`, `approval_key_jkt`, `proof_key_jkt`, `device_name_sha256`, and the current DPoP `dpop_jti`. The name digest is unpadded base64url of SHA-256 over the trimmed UTF-8 name. Replaying the JWS with a different request fails because the DPoP proof JTI must match and is consumed once.

The `GET /v1/me` route shows verified principal claims as a development probe. `GET /healthz` is liveness-only; `GET /readyz` pings PostgreSQL. Device registration binds its proof key to the current DPoP key, requires a distinct approval key, and verifies an ES256 proof of possession bound to the verified identity, both keys, device name, and current DPoP proof. Every directory, command-status, grant, ticket-issue, and revocation request checks that the DPoP key belongs to a non-revoked device. Owners can delegate only action and resource scopes contained in their own active grant; an owner scope must include `grant.manage`. Organization admins can manage grants across their organization and assign owner grants. Grant changes increment the grant version and commit audit and outbox events atomically. Host/runtime/session/command-status queries filter active grants and explicit action, workspace, and session scopes in PostgreSQL. Realtime ticket issuance binds a random 30-second ticket to one device key version, runtime, grant version, and explicit scope; PostgreSQL stores its SHA-256 digest, and the internal store consumes it atomically after rechecking current access. `GET /v1/realtime` validates mobile tickets or host credentials, sends a fresh 256-bit challenge, and consumes mobile tickets only after an ES256 proof from the registered key succeeds. Host runtime metadata and connection ID are stored; the connection ID prevents an older socket from refreshing or detaching a newer connection. Device WSS leases end within five minutes, and host leases end with the host credential. The WSS handler routes text-only queue/steer submissions to the current host runtime, persists command metadata/digests, and accepts host receipt transitions. It rechecks the current device and grant on every submission. Session snapshots, assistant streams, approval/question forwarding, mobile grant-lease renewal, and revoke broadcasts are not implemented. The server bounds request and idle time and shuts down gracefully.

Host enrollment endpoints create a pending host, installation, runtime, and opaque workspace records. The host OAuth client must be separately listed in `REMOTE_HOST_CLIENT_IDS`; its DPoP key must match the registered installation public key. An active organization member confirms from a registered phone device, and the host client confirms with the installation key. Only after both confirmations does the service activate the host and create owner grants for the host owner and confirming user. Codes are 256-bit URL-safe values stored only as SHA-256 digests. The API exposes enrollment display metadata without returning the code. The host-local user confirmation UI is not connected yet, and migration 002 requires reconciliation if enrollment rows already exist.

After activation, the installation owner can request a one-use 90-second challenge and exchange an installation-key ES256 proof for an opaque five-minute connection credential. Challenge issuance is limited to four pending and 20 per five minutes; no more than eight unexpired credentials can be active per installation. Challenge and credential digests are stored, challenge consumption and credential creation are atomic, and validation checks active host state, key version, expiry, and the registered thumbprint. The `REMOTE_HOST_CLIENT_IDS` allowlist also gates both new routes. The Relay validates the host credential, requires a fresh signed key challenge, and limits the host connection to credential expiry. It routes scoped text submissions and host receipt transitions; the DSH plugin is not yet connected to this WSS protocol.

The host plugin now writes mutating commands to a profile-local SQLite WAL journal before dispatch, stores command/result bodies with AES-256-GCM, and only reports the `agent_queued` local state after DSH session flush succeeds. Session creation also waits for its persistence checkpoint. A DSH `requestId` retry recovers a message that may have crossed the DSH boundary before a crash; other ambiguous mutations become `outcome_unknown`. The DSH CLI and current-process tests exercise journal persistence with local fixtures. The current debug IPC still uses a local principal and does not send receipts to the Go service; the durable Relay receipt path and platform key-store wrapping remain open.

## Verification and remaining M1 work

`go test -race ./...` uses generated RSA and P-256 keys plus a local JWKS test server. Coverage includes issuer, audience, client, scope, expiration, not-before, `cnf.jkt`, JWT type, algorithm, duplicate JSON keys, DPoP method, URI, token hash, public device-key validation, approval-key proof of possession, host installation proof binding, private JWK rejection, initial nonce challenge, nonce retry, concurrent replay and proof reuse. The PostgreSQL integration test applies migrations 001 through 004 and covers challenge consumption, stored digests, key-bound ticket redemption, host credential validation, runtime connection replacement, command ID idempotency/conflict, receipt transitions, and status reads when `REMOTE_TEST_DATABASE_URL` is configured. Those migrations have not been applied to PostgreSQL in this environment, and repository SQL has not been exercised against a live database. `npm run verify` includes SQLite journal encryption/reopen/failure checks, the WSS JSON Schema golden-frame test, and the DSH 0.2.1-rc.2 CLI integration using local fixtures. HTTP and WebSocket tests verify readiness behavior, anonymous denial, host-client restrictions, both key-proof handshakes, message routing, idempotent retry/conflict, receipt delivery, drain, heartbeat limits, and strict request JSON. No live identity provider, token endpoint, Android client or production TLS ingress is involved.

Configuration still needs the organization’s actual issuer, resource audience, Android public-client ID, host-client ID, `REMOTE_HOST_CLIENT_IDS` allowlist and allowed scopes. The provider must issue access tokens with the configured audience, acceptable `at+jwt` signing, and DPoP key binding. This must be confirmed against the provider rather than relaxed in code.

Before M1 can pass its exit gate, remaining work includes Authorization Code + PKCE mobile integration, user/org provisioning, PostgreSQL schema application and live integration testing, a shared multi-node replay store, connecting enrollment to an explicit local desktop confirmation UI, session snapshot/subscription and assistant-stream routing, approval/question forwarding, mobile grant-lease renewal and revoke propagation over active sockets, file-transfer controls, wrapping the local journal key with platform secure storage, wiring the Host journal to Relay and service-side `host_accepted` / `agent_queued` receipts, command reconciliation after reconnect, and failure testing.

The verifier follows [RFC 9068](https://www.rfc-editor.org/rfc/rfc9068.html) for JWT access tokens, [RFC 8725](https://www.rfc-editor.org/rfc/rfc8725.html) for algorithm and token-type checks, [RFC 9449](https://www.rfc-editor.org/rfc/rfc9449.html) for DPoP proof binding, and [RFC 7638](https://www.rfc-editor.org/rfc/rfc7638.html) for JWK thumbprints.
