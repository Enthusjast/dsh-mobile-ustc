# Android encrypted transcript cache

The foreground reader persists confirmed native history in the same owner-isolated Room/SQLCipher database as the command outbox. Cached history is separate from live assistant attempts, pending commands and interactive requests. It never becomes a resumed subscription or a command acknowledgement.

`LocalDataOwner` preserves the existing account/organization scope hash, full account/deployment/user/device fingerprint and wrapped-key metadata. `CommandOwner` remains a source alias. The database filename and its AndroidKeyStore wrapping alias are unchanged. Room schema version 2 adds cached-session metadata and ordered record rows, with an explicit migration from version 1 that retains the original command bodies, IDs, attempt counters and uncertainty. There is no destructive migration or plaintext fallback. Foreign-key cascades remove a session's records with its metadata. Account cleanup destroys the shared wrapping key before removing database files.

The reader first verifies its account and obtains a new ticket and registered-key TLS handshake for the explicit current read scope. It then calls `GET /v1/runtimes/{id}/sessions/{session_id}/read-access` with the registered phone proof. That read-only endpoint atomically checks the current session/workspace mapping, read action, user, organization membership, device/key, active host/installation/runtime and grant. It works with unavailable host content and returns no body. The client requires its exact runtime/session/workspace and the handshake grant version to match before loading disk history. A workspace hello or directory visibility alone is insufficient. Thus a reachable control plane can authorize previously cached history while the host is offline. A denied current ticket cannot reveal old rows. After loading, wall-clock and monotonic deadlines bound display to the earlier of the connection lease and the exact-session authorization. The server caps authorization by five minutes, access-token expiry and grant expiry. The client deducts the complete HTTP request duration from the returned issued/expiry interval before starting its local deadline. Restoring a database never restores an old grant, credential, subscription, cursor continuation or offline authorization. While its host is offline, the phone keeps its heartbeat/control connection and can still receive revocation. An idle cached view also rechecks exact-session authority every two seconds, including catalog-only workspace moves that do not increment a grant version. Each check has a two-second timeout and can shorten, never extend, the original view lease; inability to revalidate never renews that lease. Load and revocation-window acceptance at target scale remain separate gates. Manual retry opens a fresh ticket/subscription instead of resuming cached sync state. A cold account recovery still requires online identity/resource revalidation. After the view's lease expires, the user must reconnect and obtain current authority again.

The cache retains the latest confirmed window fetched from the host for up to 30 days from that fetch. A cache read updates eviction recency but does not extend content retention. Expired or future-dated rows are removed on load, save or directory reconciliation. The owner budget is 128 sessions and 32 MiB of encoded record bodies; an individual session retains up to 4,096 records within the reader's 8 MiB conservative content budget and an additional 8 MiB encoded-body limit. When necessary, the oldest records are trimmed from a session and least-recently-used sessions are evicted. Those operations do not discard unresolved command intents.

Only a durable prefix is eligible for persistence. Observation without a host persistence checkpoint is insufficient, and an empty opening cannot become an apparently empty offline history until its empty checkpoint is confirmed. When a checkpoint arrives before an assistant's matching committed end, the held settlement and its suffix remain excluded from the raw cached records. This prevents process recovery from exposing a reply that the live display still treats as unsettled. The display JSON encoder uses the existing independent 2 MiB record grammar and limits; it does not enlarge the 128 KiB signing/configuration JSON budget.

Cache writes use a bounded conflated channel and a serialized persistence boundary. Ordinary assistant chunks do not cause repeated writes of an unchanged confirmed cut. A new snapshot replaces its previous cached window atomically. Reconnection always obtains a fresh snapshot and paging cut. Epoch changes invalidate the old session cache. Revocation clears the visible body, retires queued snapshot generations, waits for an in-flight write and removes the affected data, so a late write cannot restore revoked history. Logout and navigation cancellation share the journal's cancellation/close and account-generation fences.

Every authoritative runtime-directory refresh, including account recovery, removes caches outside the current read scopes. Literal session and workspace grants remain distinct; empty resource arrays grant nothing. Cache rows also retain their workspace mapping, and a changed mapping invalidates the previous row. Runtime revocation removes that runtime's commands and history while preserving siblings. Sensitive views and unsubmitted composer text are cleared on background/navigation changes; cached records remain encrypted under `noBackupFilesDir` until expiry, revocation, eviction or account exit.

The UI labels disconnected content as local confirmed history, keeps retry available and does not claim that a cached task is still running. Cache I/O failure leaves online reading available and displays a cache warning. If exact-session authorization is unavailable, old disk history and its offline view remain disabled while a fresh live subscription may still read independently authorized host content. A correlated command error retains the original intent and status reconciliation without tearing down the reader/control connection. Existing secure-window and backup exclusions continue to apply. Long-offline devices cannot receive immediate remote erasure; bounded display authority and fresh revalidation are separate from encrypted disk retention.

On 2026-10-25, all 102 shared JVM tests and full Android check/lint/debug APK builds passed. The complete API 26 application suite passed 53 tests; the nine affected session/chat cases passed again on the final SDK after periodic revalidation was added. Five native storage cases and the independent encrypted migration test also passed. Validation covers shared record encoding/projection and held-settlement boundaries, real TLS authorization/lease/revocation races, Android SQLCipher/WAL/reopen/expiry/scope/capacity behavior, controller recreation with an offline host, and a real encrypted version-1-to-2 migration. The final Kotlin/Go/PostgreSQL/npm DSH composition and Go race suite passed, including exact-session cache authority with an offline host and an actual DSH catalog. All 170 host contract/type/build/tests passed as well. These scopes complement the Android fixtures; they do not establish an APK-to-Go-to-DSH device run. The dedicated migration test requires an explicitly selected secure, unlocked test device:

```sh
cd android
ANDROID_SERIAL=<owned-test-device> ./gradlew :core:data:connectedDebugAndroidTest \
  -Pandroid.testInstrumentationRunnerArguments.accountFixture=true
```

Application fixtures additionally require the existing account/network test arguments and, for the full recovery suite, the dedicated biometric fixture. Physical-device storage/key behavior, actual OS-kill/power-loss windows, school identity, product approval of the offline boundary and full M1/M2 acceptance remain gates.
