# Android signed approval client

The shared Android client now negotiates the existing [approval transport](approval-protocol.md) on its foreground session socket, reads exact online execution contexts and submits immutable signed decisions through fresh HTTPS admission. Encrypted decision storage and reconciliation share the account lifecycle. The application review/BiometricPrompt flow remains work; the standard APK has not opted into this SDK extension. The existing [question forms](android-questions.md) do not supply tool approval authority.

`ApprovalStatus` preserves control-plane decision state, host consumption/result facts and final execution outcome separately. A forwarded HTTP admission is not a host result. The parser accepts the service's RFC 3339 metadata precision, checks exact fields and routing, and requires an execution outcome exactly when the native host state is `settled`. Snapshot lists are bounded to 64 unique IDs; references must match their explicit runtime, epoch, session and request. Admission responses must match the original request binding, choice and canonical decision digest.

`ApprovalDetailsTransfer` accepts only a solicited `approval.details` response or its ordered `approval.fragment` parts. Every part carries the original request/runtime/epoch/session identity. It checks canonical standard base64, a 40 KiB part limit, at most four parts, a 128 KiB total and a three-second assembly deadline. Complete bytes go through the same strict Unicode/duplicate-member/JCS context parser as signature verification. The resulting digest, approval/execution identity, deadline and expected host must match the current reference. Partial or malformed content never becomes reviewable. Completion, cancellation and errors retire the transfer.

`SessionApprovals` belongs to one current connection and session subscription. It holds bounded metadata and at most one body/lookup. A fresh detail read creates an opaque review generation bound to the connection, runtime epoch, session, execution and context digest. Replacement, cancellation, expiry, a competing decision or connection disposal retires that generation. Both wall time and an original monotonic deadline constrain review; repeated references and clock rollback cannot extend it. Reconnection requires another online detail read. No approval context, handle, pending callback or lookup enters the transcript cache or saved instance state.

Because metadata carries no sequence, racing status reads cannot erase a known decision, consumed execution or final outcome. Conflicting decision digests, request definitions and native terminal outcomes require resynchronization. Once a request leaves pending in a connection, an older pending reply cannot make it reviewable again. These client facts describe observed state; the service's fresh authorization/assurance checks and the host's signed lease, native one-use journal and final execution guard remain authoritative.

`ApprovalDecisionIntent` retains the complete context and exact original compact JWS under a local request ID and owner binding. Creation independently verifies the current registered key and context; reopening verifies the historical signature at its original issue time so an expired proof remains available for reconciliation. Current dispatch separately enforces the request deadline and 30-second decision-age limit. Reopening never creates a new signature, review generation or callback. Allow and reject use the same record model.

Room version 4 adds a separate `approval_decisions` table to the existing SQLCipher database, with migrations from all prior versions. Context bytes and compact proof occupy separate columns so the complete 128 KiB context budget survives the extra signature. An approval keeps one original decision; local IDs share the command namespace. The journal commits an uncertain attempt before HTTPS eligibility. Same-proof retry requires explicit action, a fresh pending status and a still-current signature; stronger acceptance/end facts are committed even when they make retry ineligible. Another device's decision ends local eligibility without being attributed to this proof. Forwarding, service acceptance, host consumption and final outcome remain distinct.

Each owner retains at most 128 approval records and 8 MiB of original context/proof bytes. Capacity can evict final records; unconfirmed decisions and accepted executions awaiting host result remain retained. Attempted records cannot be manually discarded. Runtime revocation clears the affected approval records. Directory reconciliation retains them only for current owner authority with `session.read`, `approval.decide` and matching session/workspace scope; other authorized chat/history data stays under its existing policy. Closing the journal or its database owner fences further operations, and account erasure uses the existing database wrapping-key lifecycle. These records support reconciliation only and never recreate an answerable review.

`SessionApprovalAccount` supplies the independently registered approval key, current host ID and account-owned decision journal. Directory scope construction adds `approval.decide` only for an explicit client opt-in under current owner authority. It is separate from message/cancellation authority and does not require `command.status`; approval status uses its own WSS RPC. Capability absence keeps ordinary reading available and exposes no approval form or old decision body. Current ticket session/workspace scope filters saved originals before display and automatic status queries.

`SessionApprovalClient` starts one bounded watch on the existing key-proved read socket. It keeps at most 256 metadata references, 64 pending metadata writes, four correlated status RPCs and one detail/review generation. Retired correlation IDs are bounded and late details cannot restore a competing or expired review. A missing opening snapshot closes the connection for recovery; detail and status deadlines do not cancel unrelated socket reads. Host-offline state removes executable reviews while the still-authorized control connection can reconcile original status. A missing or inaccessible individual status remains uncertainty without revoking an otherwise authorized read.

Signing preparation returns complete canonical bytes for the caller's per-use key operation. Submission rechecks that same live review and choice, persists the exact signed original, then commits an uncertain attempt before HTTPS. The body carries only `connection_id` and the original `decision_jws`. Each attempt uses the currently verified resource JWT and a fresh DPoP proof. One explicit middleware nonce challenge permits another proof JTI; ordinary transport failure is not replayed. Request age, current connection, context, monotonic deadline and review generation are checked again immediately before each HTTP call. Server assurance failures stay explicit and cannot become a local MFA claim.

HTTP waits hold no reader/model lock, so revocation, competing decisions and expiry continue retiring authority while a response or resource-client mutex is blocked. The connection lifetime also owns the HTTP call. Manual retry queries the original status, persists stronger proof even when retry is refused, and serializes rearm/attempt persistence against background reconciliation. It uses the same signed bytes and never creates a replacement decision automatically. Reconnect only reads and reconciles existing records; another online context lookup is required before an explicit same-proof transfer.

Validation covers shared context bindings and hostile status/routing/fragment inputs, Unicode reconstruction, native result/delivery distinctions, current-host checks, competing decisions, late metadata, clock/expiry limits, replacement handles and connection disposal. Platform key signing already has separate [Keystore evidence](android-keystore.md). School configuration remains unavailable and development continues with the authorized local identity/model fixtures. Physical-device policy, production provisioning and complete M1/M2 acceptance remain gates.
