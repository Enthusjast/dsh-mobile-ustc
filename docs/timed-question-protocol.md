# Timed questions over Relay

Both peers negotiate `question.timed.v1`. Viewing also requires `session.read.v1` and current `session.read` resource scope; answers use `command.relay.v1` and explicit `question.answer` permission. The blocking-question capability and frames remain separate. Timed questions and plan choices never mint tool approval tokens.

Relay adds `timed_questions: true` to the authenticated host's subscribe payload only when both peers support it. The host then publishes `question.timed.snapshot` with the current subscription/sync identity and payload `{revision, items}`. Each item has `question_id`, projected `questions`, `state` (`open`, `continued`, `reply_queued`) and nullable `expires_at`. An unclaimed open question has no fabricated deadline; a claim supplies native timing. Continued/queued views have no foreground expiry. Snapshots replace the current list, have process-local revisions and use the existing bounded content fragmentation/queue rules. They are not native persistence checkpoints.

The phone sends `question.claim` with request/runtime/epoch/session/subscription/sync UUIDs and payload `{question_id}`. This request UUID identifies that claim for its whole lifetime. It must belong to the exact authenticated phone socket's open sync; another socket for the same device cannot borrow it. Admission rechecks current host ownership and both read/answer authority. A claim affects execution timing, so read-only authority is insufficient. Claims are transient and never enter the command journal or database.

The host attaches native `userQuestions.attachWait` with a lifetime owned by that routed subscription. It responds with `question.claimed` using the original request UUID, sync identity and payload `{question_id, remaining_ms, expires_at}`. `remaining_ms` is measured at host admission; clients must not extend it by network delay or restart a fresh full countdown on reconnect. The host also enforces the native deadline. `question.claim.closed` ends the claim, with question UUID and code `question.ended`, `interaction.stale`, `rate.limited` or `internal`. Relay checks current host/phone authority again before delivering timing or terminal metadata. Authorization/authority failure drops the subscription and aborts its host followers/claims.

`question.release` uses a fresh request UUID, the same subscription/sync routing and payload `{claim_id}` naming the original claim request UUID. Relay removes that claim route, forwards release and acknowledges `question.released`. Repeating release is safe. A failure to deliver cancellation closes the host transport to ensure its native claims are released. Unsubscribe, socket loss, host replacement and revoked connections also release claims through follower teardown. Release does not answer the question or cancel the Agent; native foreground timing resumes and may produce a continued question.

At most four claims are active per subscription. A subscription remembers at most 256 admitted claim UUIDs, including ended ones; none may be reused in that subscription. This prevents a delayed terminal frame for an old claim from closing a newer one. Replace the read subscription when this lifetime limit is exhausted. Host subscriptions share existing queue limits; the native adapter additionally caps eight claims per question and 128 across that host. Late frames for released or replaced routes are discarded.

The answer command is `question.timed.answer`, with request/runtime/epoch/session UUIDs and payload `{question_id, answers}`. It does not require an open claim or subscription, but requires the current question-answer resource permission. Its SHA-256 digest covers JCS `{type, runtime_epoch, session_id, payload}`. Native state decides whether this is a foreground callback answer or a new continued reply; caller-supplied native call IDs or a delivery mode are not accepted.

Foreground answers consume the current callback once, persist their command result and report `settled`. Continued answers call native `userQuestions.answer` and steer a new `user-question-reply` message. They report `agent_queued` only after the session flush checkpoint succeeds. This acknowledges durable queue admission; the native message and subsequent turn/checkpoint establish observation and completion. A failed checkpoint reports `outcome_unknown`, and a matching retry cannot enqueue the reply again. Epoch/body conflicts and competing stale answers are rejected. No late answer completes the old timed tool result a second time.

The shared Schema/goldens cover timed snapshots, Unicode answer digests, claim/release and terminal frames. Go tests exercise socket/sync isolation, read-only and legacy denial, per-frame authorization, capacity, retired UUIDs, explicit release, unsubscribe and disconnect cleanup. Host tests exercise native deadlines, reload, actual late-message delivery, command retries and failed checkpoints.

`npm run test:remote-dsh` runs the actual Go entrypoint, isolated PostgreSQL and installed npm DSH 0.2.1-rc.2. A private test preset copies the installed standard preset and configures its native question tool for timed mode; the ordinary standard preset remains available for blocking-question checks. The test validates foreground claim/answer, foreign-socket denial, release and retired-ID denial, continued state after release/unattended timeout, persisted late-message admission and retry, REST status, and absence of question/answer bodies in the Relay dump. Its phone fixture paces sends within the production operation quota. Identity/model/key providers are local fixtures. The [Android timed form](android-questions.md) claims only on explicit answer intent, deducts request-to-reply delay, releases exact subscription ownership and labels continued replies as late queue admission. Its active callback state is never recovered from disk cache. Production identity/key provisioning, physical-device timing, target-load/failure-window measurements and signed tool-approval UI remain separate acceptance gates.
