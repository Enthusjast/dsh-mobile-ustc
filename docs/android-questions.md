# Android questions and plan replies

The foreground reader negotiates `question.blocking.v1` and `question.timed.v1` with its existing session read connection. Routed snapshots share the current runtime/epoch/session/subscription/sync identity and bounded fragmentation path. They update a separate transient question model, not the native transcript, persistence cursor or encrypted history cache. Reconnect, revocation, backgrounding and navigation remove answerable forms and unsubmitted input; cached history cannot recreate a pending callback.

The display model preserves exact question IDs, text/detail/header, option labels/descriptions, multi-selection and plan-review intent. Each current kind has its own monotonic snapshot revision; older repeats cannot restore an ended list and changed repeats require resynchronization. A question ID cannot silently acquire a different definition in the same stream. Definitions and a live routed handle bind each form. A replacement sync retires old handles; outstanding native claims force a new subscription so their lifetime is actually released.

Read authority may display a question, but answers and timed claims require explicit current `question.answer`, `command.status` and negotiated command capability. The UI starts with no invented selections. Blocking answers require one valid response per current prompt; timed prompts may explicitly remain empty according to native skipped-answer semantics. Known labels and cardinality are checked again at submission. Plan review shows its full projected detail and does not enable continuation while detail remains collapsed. A plan reply never produces a tool approval token or substitutes for the signed-approval execution context.

`question.answer` and `question.timed.answer` share immutable epoch/session/question/answer identity and the existing Go/TypeScript JCS digests. The original structured reply is encrypted before dispatch, and the attempt is committed uncertain before a socket write. Exact labels and custom Unicode/whitespace are retained. A local `local_context_sha256` binds the stored intent to its projected definition; this field is never included in the wire frame or wire digest. Older message/cancel/create storage remains byte-compatible and Room schema version 3 is unchanged. Missing question context or same-ID context replacement is rejected.

The shared sender revalidates current question identity, definition, epoch, expiry and answer shape before dispatch, including manual retry after reconnect. It never replays an attempted answer automatically. An unresolved or confirmed same-question reply prevents creating another intent until the existing result is reconciled; rejected replies can be corrected against a still-current question. An explicit retry remains limited to fresh own-device `received` status without proved host save. Stronger status facts are saved even when they make that retry ineligible. Native one-use consumption and its journal remain authoritative across competing devices and local answerers.

Timed forms claim native waiting time only after an explicit user action to answer. Claims are transient subscription controls, do not enter the command journal, and are limited to four active and 256 distinct IDs per subscription. Before native timing arrives, the UI does not invent a deadline. The claimed deadline deducts the complete client-to-reply delay from host remaining time and is bounded by host expiry; releasing/reclaiming cannot reset an already known deadline. Release uses a fresh request UUID naming the original claim. Late timing for retired claims is ignored. Missing claim/release completion triggers subscription replacement so host followers and claims are released rather than left indefinitely waiting.

Closing or leaving a form releases its timing ownership; socket loss, scope change and foreground/account disposal close the reader and release host followers. Release does not answer or cancel the Agent. The phone does not infer `continued` from its own timer: it waits for current source state. Native continued replies use `question.timed.answer` and the native late-message path. `settled` means a foreground answer was consumed and persisted, not that the task finished; `agent_queued` means a late reply crossed its flush barrier. The UI labels these separately and never completes the old timed tool result twice.

Validation is separated between shared grammar/digest/storage/context tests, routed snapshot/fragment/revision/expiry tests, real TLS answer and claim/release fixtures, Android platform-key/controller/Compose/persistence cases, and actual npm DSH composition. The SDK composition drives blocking answer consumption, timed foreground claim/answer, explicit release and a continued late reply observed in native history. School identity, physical-device policy, OS kill/power-loss windows, notifications, signed tool-approval UI and complete M1/M2/scale acceptance remain gates.

On 2026-10-25, all 124 shared JVM tests, Android check/lint and debug app/test APK assembly passed. The complete API 26 application suite passed all 72 tests, including five question-form cases, three platform-key/controller question cases and nine command-persistence cases. These verify exact single/multiple selections, complete free-text batches, read-only and continued forms, exclusion of unsubmitted answers from saved state, context-bound encrypted reopen, lost-receipt reconciliation without another answer write, and release followed by late queue admission. An earlier full run stopped during emulator lifecycle teardown and the QEMU process exited; that incomplete run is excluded from passing evidence. The final run used a fresh owned AVD, with its test PIN/fingerprint and system-animation settings confined to that fixture; it completed in 553 seconds and the emulator was then shut down.

The same day's `npm run test:remote-kotlin` passed with Go race detection, isolated PostgreSQL and installed npm DSH 0.2.1-rc.2; all 173 host tests and contract/type/build checks also passed. This establishes shared Kotlin/Go/DSH behavior separately from native Android behavior against fixture peers. It does not establish an APK-to-Go-to-DSH physical-device run or deployed school identity.
