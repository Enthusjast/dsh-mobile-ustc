# Durable host approval result reports

The private command/approval SQLite database now uses schema 3. Version-one command journals and version-two approval journals migrate after the existing encryption-key check. Context/decision encryption, AAD, nonce/execution tombstones and one-use execution semantics remain intact. An older reader that only understands schema 2 refuses the newer database.

Each approval carries a remote-registration fact, a pending-report flag and a retry deadline. Receiving a matching `approval.registered` status records only that the control plane knows the binding; it never approves a native invocation. A verified/admitted signed decision also establishes that fact, including when the registration acknowledgement races the decision. Existing decided version-two records enter the report queue during migration so their execution history is retained. Legacy unacknowledged pending records remain local audit history and never acquire authority.

Every known state transition marks its latest metadata fact pending in the same transaction: approved/denied, consumed, settled, expired, cancelled, invalidated and unknown. Result payloads contain only runtime/epoch/session/approval/execution identifiers, binding/decision digests, state and a fixed final outcome. Full contexts, native call IDs, nonce, phone JWS, authority evidence and tool arguments stay in their existing encrypted records and are not part of a report.

`takeReports` reserves at most 64 due facts (16 by default), verifies their encrypted source data and commits a bounded retry deadline before returning frames. A transport retry uses the same full JCS SHA-256 and a content-derived UUIDv8 correlation ID; the complete digest, not the truncated UUID, identifies the acknowledged fact. Reserving one entry delays that entry rather than starving later reports. A state change resets its deadline immediately, so a new final result is not held behind a prior approved/consumed receipt. `retryReports` allows a replacement connection to retry pending metadata promptly.

`acknowledgeReport` clears a fact only when its exact fingerprint still describes the current local record. A late approved acknowledgement cannot erase consumed/settled work; a consumed acknowledgement cannot erase a newer native outcome. Matching duplicate acknowledgements are idempotent. Failed or ignored updates never manufacture a cleared queue. The sender must additionally validate the authenticated connection, wire acknowledgement/routing and server status before passing a fingerprint to this internal method.

Closing/replacing the journal owner invalidates unconsumed work and marks spent but unobserved work unknown. Unacknowledged settled facts keep their original epoch, outcome, correlation ID and digest across reopen. Reading/reserving/acknowledging an old fact does not restore a callback, decision token or executable permission. Clock/owner/storage fences still apply, and a reservation storage failure closes the handle to further execution authority.

Tests cover reservation/retry identity, out-of-order acknowledgement, cancellation racing registration, bounded/fair retries, settled/unknown recovery, version-two migration, ignored acknowledgements and failed reservation writes. The [normal sender/native owner](approval-native.md) now connects this persistence boundary to WSS and the plugin lifecycle; its cache/receipt and native body checks remain separate required steps.
