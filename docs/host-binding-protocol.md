# Host binding review and activation

The installation starts a five-minute enrollment using its separately allowlisted host OAuth client, installation proof key and a random 256-bit code. An active organization member uses an independently registered phone client/key to confirm. The host must then review that user, prove its own installation key and confirm independently. A host-first confirmation is rejected; it cannot preauthorize an unknown later phone user. Host OAuth clients are denied phone device registration, current-device lookup and phone-protected resource routes; the host's own enrollment status read remains available with the correct installation key. Client/key separation does not constitute physical-phone attestation or production school policy acceptance.

`POST /v1/enrollments/{id}/preview` requires the registered phone proof, current organization membership and the exact unexpired code in the JSON body. It is read-only and returns no code/private key. It exposes the public installation JWK thumbprint and `user_confirmed_by_me`, derived from the authenticated service user, for an explicit review. Codes are not query-string credentials. Wrong/expired codes or inaccessible applications return a generic denial without disclosing their metadata.

`GET /v1/enrollments/{id}` is for the initiating owner or confirming user, not an arbitrary organization member with an ID. Phone reads require an active registered key. Allowlisted host reads additionally match the stored installation thumbprint. This participant read supports reconciliation after a dropped confirmation response without keeping or resending the code. An approved historical application does not replace current resource authorization.

`GET /v1/enrollments/{id}/host-review` is limited to the installation owner with the matching installation DPoP key and host client; revoked hosts, installations and runtimes are denied. It rejects query selectors and returns the enrollment plus the confirmed user's internal UUID, issuer, subject and current organization eligibility, or `null` before confirmation. The ordinary status and phone preview responses do not expose these host-only fields. The issuer and subject are the existing verified identity key, not a display name or an email-based account match; the host must use a trusted organization directory when a human-readable identity is needed. Render these strings as untrusted text and do not log them as a substitute for the bounded audit metadata.

After explicit local review, `POST /v1/enrollments/{id}/host-confirm` requires both the enrollment code and `confirmed_user_id`. The server compares that ID with the phone confirmation inside the same locked transaction and rechecks that both users are active organization members, the host/installation/runtime are not revoked, and the confirming device and its recorded key version remain active before creating grants. The phone confirmation itself rechecks the request's DPoP thumbprint against that device inside its transaction. Mismatched IDs, revoked targets or devices, rotated device keys and premature confirmations fail without granting access. The review's `eligible` field reflects these current conditions but is not an authorization lease. A retry for an approved enrollment must still name the original confirming user; revoked targets are denied. The audit record includes the reviewed internal user UUID, not the code or subject. This API enables, but does not itself implement, the host's local confirmation UI or prove that a person inspected the review.

Apply migration `031_enrollment_confirmation_device` before starting the new service. Pending host-first confirmations written by an older server are not presented as reviewed confirmations and are cleared transactionally when the first phone confirms; that phone cannot activate the enrollment without a new host confirmation. Pending phone confirmations from older servers have no recorded device and must be explicitly confirmed again from an active device. The same user can also reconfirm after a device or key change; this clears any earlier host decision. Already approved historical enrollments are not retroactively invalidated or certified by this change: operators must review existing grants and revoke/rebind where policy requires it. The migration refuses rollback after recording device provenance. During a mixed-version rollout, disable enrollment or drain older nodes until all nodes enforce the new rule. Host integrations must update their confirmation request to include the reviewed user ID before enabling enrollment; old code-only requests are rejected.

Phone confirmation keeps its original enrollment identity. Another phone account cannot claim an existing confirmation, including through an approved idempotent retry. Activation and owner grants for the installation owner and confirming user remain in one transaction after both confirmations and current membership checks. Audit/outbox metadata excludes the code; storage retains only its digest.

An already active physical host is insufficient to activate a newly enrolled profile/installation. Runtime connection admission/refresh, authoritative connection leases, directory access, tickets, grants, command/session and approval authorization all check that no unapproved enrollment exists for the target runtime. An installation can obtain/retain a connection credential only while it has a usable approved runtime. A shared installation with an approved profile can keep using that profile but cannot attach its pending sibling. Legacy runtimes with no enrollment retain the prior explicitly provisioned path; API creation always inserts the pending enrollment in the same transaction as its new runtime.

Migration 008 adds a partial index of unapproved runtime enrollments for these authorization checks. It changes no message/body storage and requires no copied identity data. Apply it after 007. Eligibility comes from the authoritative enrollment state and resource/key/grant checks, not from the presence of an index or a client's directory snapshot.

Expiry revokes the particular pending runtime. The installation is retired only after no nonrevoked runtime remains, and a pending host is retired only after no installation needs it. This preserves both already approved siblings and pending siblings that can still complete their own confirmation. Existing approved resources continue to use normal key, grant and membership revocation. Expired preview codes do not disclose another user's pending metadata; participants can still read their own expired status.

With migration 036, an otherwise valid installation owner can [enroll a retired profile name again](installation-profile-management.md#撤销后重新登记) using a fresh request and code. This creates a new pending runtime and new workspace UUIDs; both confirmations are required again. An unrevoked runtime still reserves its name, even with an expired enrollment. Old request retries reconcile the old UUID; old grants, sessions and decisions never move to the replacement. A revoked installation cannot be reused. Apply the migration before rolling out the service, then enable reenrollment after all nodes are updated; older nodes can still reject retired names. Rollback of the schema refuses duplicate historical names rather than deleting records.

PostgreSQL tests cover code/issuer/organization isolation, no preview mutation or grants, actor-relative attribution, competing confirmations, host-first refusal, reviewed-user mismatch, legacy pending reset, membership removal, proof-key mismatch, device revocation and key rotation, reconfirmation, migration rollback, profile expiry isolation, no pre-confirmation credential/connection/ticket/grant access and changed enrollment state invalidating a current lease. HTTP tests verify registered-phone protection, host-key-bound status and review, client-role separation, strict bodies and no-store responses. The Go/PostgreSQL/DSH composition uses local phone and host protocol fixtures. These are fixture results. The production host confirmation UI, school registration/DPoP configuration, organization administrator policy, physical device behavior and full milestone acceptance remain gates.
