# 控制事件的逐节点消费

生产入口现在为每个进程登记独立 consumer，通过迁移 019 的确认表和事务快照消费 `control_outbox`。一个节点确认不会移除另一个节点的待处理事件。当前保留原来的事件用途与本地应用逻辑：设备 / grant 撤销关闭对应手机，审批失效绑定当前 Host 连接，详情和状态引用仍从权威状态重新读取。

## 节点身份与失败关闭

`REMOTE_RELAY_NODE_ID` 可配置稳定 UUID，多个同时运行的节点必须不同。稳定身份重启后保留已覆盖范围及未确认事件。未配置时使用本进程新建的 ephemeral UUID，首次登记前的状态由当前数据库授权与重新订阅建立；该身份不承诺跨重启追尾。

每次登记使用新的 generation。活跃稳定身份不能被第二个进程接管；旧 lease 结束后新代次可接管，但旧代次不能读取、确认、续期或释放新代次。consumer 所有权期限为十秒，每秒更新，操作受两秒 context 约束；这是分发者身份，不延长任何业务授权租约。续期无法确认、代次失效或控制数据无效时，进程停止业务接入、关闭升级连接并退出。正常停止先 drain，再释放自己的所有权。

## 提交时序与检查点

使用 [PostgreSQL 的完整事务 ID 和快照可见性](https://www.postgresql.org/docs/18/functions-info.html)，不使用 UUID、自增 ID 或事件 created_at 作为提交顺序。事件生产者由数据库强制记录顶层 `pg_current_xact_id()`；事件身份、组织、用途、内容、创建时间与生产者不可修改，只有原 `published_at` 标记可更新。

consumer 保存 coverage snapshot：对该快照尚不可见、目前已提交、且该节点未确认的受支持事件均需消费。即使事件在节点启动前写入、时间戳很旧或后来才提交，它仍然可见于待处理集合。一个生产事务的多条事件也必须全部确认。

读取时先锁定当前 consumer 并校验代次和期限，再捕获新 snapshot，最后查询候选。只有没有候选时才推进 coverage 到先前捕获的 snapshot：在之后才提交的事务不在该 snapshot 中，下一次仍会读取。快照仅作为持久数值保留，不保持长事务或导出快照。

本地应用完成后再插入 `(node_id,event_id)` 确认。确认失败不推进覆盖范围，之后幂等重放。推进检查点后，每次最多删除 512 条已覆盖确认，避免一次清理阻塞续期。旧 ephemeral 身份在过期十分钟后分批清理；稳定身份保留，不能以清理代替离线重放。

`published_at` 现只表示至少一次本地处理成功的兼容诊断标记，不表示所有节点已处理，也不参与新消费者的候选筛选或确认清理。不得据此删除仍可能被其他节点或晚提交事务需要的源事件。源 outbox 保留策略尚未在本阶段自动回收。

## worker 与边界

outbox 250 ms 轮询与原一秒权威连接检查继续独立，128 条批上限和整个权威检查的两秒失败关闭保持不变。节点所有权另行维护；历史清理失败记录 `consumer_cleanup` 指标，不冒充租约丢失。业务 `control_event_age_seconds` 现在由每个进程各自观察，不能将一个进程的样本当成全节点完成。

事件应用 / 确认表示本地失效、通知 / 连接关闭或当前状态引用排入队列，不表示原生工具已经执行或所有客户端展示完成。命令正文和临时流没有写入 outbox / 确认表。不同节点的手机、Host 和订阅仍需后续跨节点路由，本阶段没有通过消息代理转发业务正文。

## 2026-10-27 验证

私有 PostgreSQL / race 回归 `.local/control-consumer-postgres-first.log` 与 `.local/control-fanout-security-final.log` 验证独立确认、全局标记不吞其他节点事件、旧时间戳 / 嵌套事务 / 晚提交 / 检查点、重启与离线事件、旧代次 fencing、失败确认回滚、ephemeral 清理、512 条检查点清理及事件不可变。worker 用例验证失去所有权会取消阻塞分发，取消可正常退出，无效控制数据不能继续服务。

两个真实生产 Go 进程经同一校验证书 TLS 1.3 入口，使用共享认证状态和真实手机 ticket / WSS 证明。相同设备分别连接两节点，一次实际 revoke 在两边关闭并由各自确认；另一个设备继续心跳。稳定节点离线期间的第二次 revoke 在重启后重放，已撤销设备不能重新获取 ticket。强制更换 consumer generation 后，实际进程退出，升级连接关闭。最终定向记录 `.local/control-fanout-security-final.log`，该进程用例约 1.79 秒。

完整 PostgreSQL race suite 与本机 npm DSH 0.2.1-rc.2 组合也已通过，记录 `.local/control-fanout-full-first.log`，原生链路约 11.962 秒；其后增加的不可变 / 有界清理 / 真实代次失效断言由最终定向回归验证。该组合继续证明正常插件的高风险调用在撤权后被阻止及原生结果对账。学校身份、物理设备、集群 12000 / 40000 源帧每秒、跨节点路由与安全备份恢复仍是独立出口。

最终完整回归 `.local/control-fanout-full-final.log` 再次通过，实际 npm DSH 组合约 11.975 秒；`go vet ./...` 通过。开启新 consumer 的生产进程也通过相同单节点 3000 连接、200 活跃会话 × 20 Hz、30 秒：120000 帧全部交付，准入 6.650 秒、客户端 p95 33.134 ms / p99 83.132 ms，Go route 的 300 ms 桶比例为 1，撤权样本 67.09 ms。记录 `.local/control-fanout-3000.log` 与 `.local/relay-capacity/control-fanout-3000/`，报告明确记录 `postgres_per_node_snapshots`，不混写成两节点业务路由负载。

快照检查点属于当前数据库事务历史。安全恢复不能沿用回退 / 异构数据库的旧覆盖状态直接服务，也不能仅清空确认表来恢复；需要先使旧凭据 / 连接失效并同步当前权威状态，再按恢复方案建立检查点。这一恢复演练尚未在本阶段完成。
