# Device enrollment reconciliation

An interrupted `POST /v1/devices` can leave the phone uncertain whether its original keys were accepted. Repeating a device creation with new keys loses the original enrollment. The development client now retains the current keys while this foreground login is alive and reconciles by read before offering another authenticated registration.

`GET /v1/devices/current` requires the ordinary resource JWT/DPoP middleware. It uses only the verified issuer, subject and token-bound proof key. It does not accept a target device ID or a replacement key from a query parameter. The active service user and this user's matching device are read in one PostgreSQL statement. A missing or inactive user receives 403; a database outage receives 503. The normal `no-store` envelope contains one of:

```json
{"ok":true,"data":{"state":"unregistered"}}
```

```json
{"ok":true,"data":{"state":"active","device":{"device_id":"22222222-2222-4222-8222-222222222222","key_version":1,"approval_key_jkt":"<registered approval JWK thumbprint>","proof_key_jkt":"<registered proof JWK thumbprint>"}}}
```

The same device fields can accompany `state=revoked`. The response includes no device name, another account's devices, public-key bodies or credentials. A revoked key can read its own registration state with a valid current account token/proof, but still cannot use protected directories, tickets or commands. Reading this status creates no user, membership, device, grant or audit mutation.

The Android client first validates `/v1/me` and its configured organization, then compares both returned key thumbprints and the explicit key version against its current handles. It supports enrollment version 1; a different version or revoked device ends this local session. An active exact key pair resumes the registered directory. An absent record permits a fresh, explicit biometric registration. A registration write is never automatically replayed by the HTTP client. After a write failure, a read resolves the outcome; a failed read leaves a distinct **核对设备登记** action that queries status only. The app performs another status lookup before preparing a new registration.

An absent read is a snapshot: an earlier write can still be settling. To make an explicit retry safe, the service also treats the same verified account, proof/approval key pair, normalized name and version 1 as one enrollment. Every retry still needs a fresh valid approval-key JWS bound to that request's DPoP JTI; old HTTP/approval proofs cannot be replayed. PostgreSQL's unique-key conflict handling waits for an in-flight insertion, and a second statement locks/reads the committed device. Exact matching active data returns its original device UUID; different account/name/keys/version returns `device.registration_conflict` (409), and a revoked device is denied. A retry never changes the existing keys, name, version or revocation state. Only the first insertion writes `device.register` audit metadata, in the same transaction. Matching retries keep the existing 201 response shape for compatibility.

On 2026-10-24, the isolated PostgreSQL race suite verified eight concurrent registrations settling to one device and one audit row, changed-data/account/key conflicts, no cross-account status disclosure, inactive users, key-version rollback denial, revoked-device reconciliation and failure during database outage. The HTTP suite checked that caller identity/key selectors are ignored, that status is available before enrollment and that failures disclose no device data. The real Go/PostgreSQL/npm DSH 0.2.1-rc.2 chain checked a fresh-proof matching retry, the active current-key response and a revoked sibling's status. School identity and Android are not part of that CLI chain.

Kotlin's real local HTTPS fixture deliberately disconnects after receiving a registration POST. It verifies that only one POST was sent, resolves the accepted key pair through GET, and rejects revoked, changed-version or mismatched-key responses. All 18 shared JVM tests, Android lint, app/test-APK assembly and all five application/UI tests passed; the API 26 UI run separately exercised the explicit query action. These are component tests; they do not constitute a real school/Go/Android registration-loss test. The store's 160-character name limit now counts Unicode code points consistently with the HTTP boundary; the concurrent test also uses a 160-character Chinese name. This uncovered the runner's implicit SQL_ASCII database encoding: it now initializes the disposable cluster explicitly as UTF8, and each Go integration database checks that encoding before testing.

The [encrypted account lifecycle](android-account-recovery.md) now persists the original keys, credential state, device name and registration checkpoint. A new controller reopens that record and queries the same key pair before exposing the directory; the pending-key ledger protects its authenticated scope. Unknown refresh outcomes require browser reauthentication while retaining the accepted device. Explicit local exit clears the vault and keys but does not revoke a remote device. OS process-kill/restore acceptance, missing/invalidated platform-key repair, service-side orphan-device cleanup and real school identity remain open; M1/M2 have not passed their full exit gates.
