# Session reads over Relay

Both peers negotiate `session.read.v1`. The ticket and current runtime grant must explicitly include `session.read`, plus the session UUID or its registered workspace UUID. `session.list` grants directory access only. New owner enrollments include the read action; existing grants need an explicit grant update. The Relay checks current device key/version, active membership, exact grant version, session state and both resource scopes before admission, pagination and every content frame. It also rechecks the current installation/runtime connection before routing host content. Database failure stops delivery.

The authenticated runtime directory now returns `organization_id` and the current user's `access` snapshot (role, grant version, exact action/workspace/session scope and optional expiry). Session directory rows include `workspace_id`, a registered opaque UUID or null. These fields let a phone choose a ticket scope from actual service authority rather than inventing a workspace or treating `session.list` as body-read permission. Prefer an explicitly granted session UUID; otherwise use its returned workspace only when that workspace is present in the current grant. Null workspace mappings require an explicit session grant. Scope containment remains literal: the client cannot turn a workspace grant into a new session-grant claim by guessing an ID. Directory metadata itself is not a credential; ticket issuance and subsequent routing independently recheck current authority.

On 2026-10-25 the isolated PostgreSQL race suite verified current-user grant isolation, opaque/null workspace mappings, a directory-derived read ticket, grant-version changes, revocation and issuer isolation. The real Go/npm DSH 0.2.1-rc.2 integration also checked the activated phone's own directory scope and the new session's opaque workspace mapping. No host path, native session identity or chat body was added to directory responses.

The phone sends `session.subscribe` with request/runtime/session UUIDs and an optional `max_messages` from 1 to 100 (default 30). The Relay first replies `session.subscribed` with a fresh `subscription_id` and current `runtime_epoch`, then forwards the request to that host. The subscription belongs to this authenticated socket, including when another socket uses the same device key. The host opens the current DSH controller's native follow; it never starts a second Agent or writer.

The host creates a `sync_id` and sends `session.snapshot`, followed by projected `session.event`, `session.checkpoint`, and `assistant.start/chunk/end` frames. Every frame carries the subscription/request/runtime/epoch/session identity and, for content, the sync identity. Native event positions and process-local assistant attempt/revision/index positions remain separate. Checkpoints report `persisted` with `through_seq`, or explicitly report unavailable/failed; an observed event alone is not a persistence acknowledgement. Session projection removes configuration and provider replay metadata. A native `user/message` is exported for explicit human input (`source.kind = user`) and an answered native late question (`user-question-reply`, with `outcome = answered` and a call identity). Injected, unknown or unattributed user-role context becomes an empty `cursor` record at the same native position. The phone preserves human replies without misattributing model-facing context, and source metadata is not exported. Bodies and assistant chunks are never written to the Relay database or audit log.

Peers that also negotiate `question.blocking.v1` receive [question snapshots](question-protocol.md) on the same scoped subscription. They replace the current pending list and have an independent ephemeral revision. They share content fragmentation/queue limits and per-frame read authorization; answering requires the separate `question.answer` action. The separately negotiated [timed protocol](timed-question-protocol.md) adds question.timed.snapshot, subscription-bound claims and native continued replies.

For `session.page`, the phone includes its subscription and epoch, plus payload `sync_id`, `through_seq`, `before_seq`, and optional `max_messages`. The host checks that the sync is still open and that `through_seq` is exactly the opening snapshot cursor. The reply is `session.page.result`, with the page request UUID and the original sync. At most four page requests may be pending per subscription. The Relay checks response correlation and sync identity; late responses after cancellation are discarded.

`session.unsubscribe` releases only the follower. It does not cancel the Agent. Relay returns `session.unsubscribed`, removes the route, and asks the host to abort its follower. Socket loss and host replacement also release subscriptions. Reconnect opens a new subscription and a replacement snapshot; old subscription IDs are never reused by Relay. Consumers discard frames for released subscriptions, clear assistant transient state when the runtime epoch changes, and request a replacement snapshot on missing native/assistant positions. The Android merge/cache implementation is still pending.

The UTF-8 envelope limit is 64 KiB. A larger projected payload becomes consecutive `session.fragment` frames carrying the same routing and sync fields; payload contains the original type, fresh `fragment_id`, zero-based `index`, `count`, and base64 `data`. Decode each fragment to bytes, concatenate in order, decode UTF-8 once, and parse the resulting JSON payload. Fragments may split a Unicode character. The logical payload limit is 2 MiB, with at most 52 fragments of 40 KiB decoded bytes each. Relay validates ordering, identities and the byte limit without reassembling content. Clients must validate the reconstructed payload and atomically apply a complete snapshot; partial snapshots never replace the current view.

There are at most 16 subscriptions per phone socket, 32 per host connection, and 16,000 in this Relay process. Phone read operations share the message-submit quota of 20 requests per second. Host followers read independently of network writes, with 3 MiB queued per subscription and 12 MiB queued across that host client. Writes also obey the connection's 512 KiB socket budget and five-second deadline. Overflow aborts that follower and reports `protocol.resync_required`; a logical payload above 2 MiB reports `protocol.snapshot_too_large` (reduce the requested history window). A single oversized native record still requires a future display/page adaptation. Relay slow-peer writes close the phone socket, releasing all of its subscriptions.

Tests use npm DSH 0.2.1-rc.2 with a loopback protocol peer to exercise snapshots, assistant chunks, history and replacement syncs in the same Agent. Go WSS tests separately exercise signed peers, connection isolation, unsubscribe, fragmented snapshots, and scope revocation. The isolated PostgreSQL 18.6 suite verifies real read authorization SQL and grant-version/key/resource denial. The [combined Go/DSH test](go-dsh-integration.md) also verifies idle device/grant revocation through the production entrypoint. [Single-process revocation workers](revocation-propagation.md) release affected connections and subscriptions. A real Go-to-DSH-to-Android chain, production identity/credential provider, durable multi-node revocation fanout, header/projection baselines, large-record adaptation and load targets remain open.
