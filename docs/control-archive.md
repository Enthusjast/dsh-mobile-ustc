# 控制事件归档与恢复代次

迁移 `022_control_archive` 为控制事件增加受数据库权限保护的历史表和管理命令。归档在单个
事务中复制源行及仍存在的节点确认、删除热 outbox 行、保存不可变批次结果，并写入审计。
任何步骤或 commit 失败均整体回滚；它不改变命令、授权、审批或文件状态。

这是**同一 PostgreSQL 数据库中的历史表**，不是外部加密冷存储、独立备份或生产 RPO/RTO 验收。
审批决定证明和审计日志的完整冷归档、外部导出、加密密钥管理和自动到期清理仍需独立完成。
历史表保留原 outbox 全行 JSONB 和确认元数据，可能包含资源 ID 与摘要；应由数据库 ACL 限制
访问，并使用组织的数据库访问审计。应用没有新增公开归档读取或删除 API。

## 何时可以移动

只处理当前控制消费者支持的九类 device / runtime-grant / approval 事件，未知主题、文件事件
及其独立消费者继续留在原表。创建时间至少 90 × 24 小时的事件才可进入候选；时间用于保留期筛选，
不作为提交顺序或消费者覆盖证明。

当前数据库代次的事件还必须同时满足：

1. `published_at` 非空且也至少已有 90 天；它只是一项兼容标记，不能单独证明所有节点处理。
2. 每个同代 consumer 的持久 coverage 快照已看到生产事务，或者该 consumer 已确认这条事件。

cutoff 和保留截止时间来自同一事务内的 PostgreSQL 时钟；运行环境需要保持数据库时间同步。

稳定节点即使离线也参与检查，未覆盖/未确认的事件保持在热表；不会为了归档自动退役稳定
consumer。短暂节点按既有规则到期清理。恢复后如果短暂节点仍有旧代次热表确认，清理会等待
这些事件连同确认归档；数据库触发器也阻止直接删除该节点而级联丢失旧确认。

旧代次事件只在当前数据库已 ready、且存在以该代次为 source 并已 release 的恢复记录时考虑。
它们仍须超过 90 天，但可以保留原先未发布的状态；隔离已取消旧凭据和连接，归档不会将其
当作当前待执行事件。程序不把来源数据库 XID 与新数据库快照比较。未知代次、未知主题和
不满足条件的事件留在热表。

事务只锁定选中的源事件；每批默认 64 条、最多 128 条。事件完整复制到
`control_outbox_archive`，复制时仍存在的每条确认及其原行进入 `control_event_ack_archive`，
再删除源事件及其热确认。之前已经被正常 coverage 检查点压缩的确认不会凭空重建。确认历史
不依赖 live consumer 外键，因此后续短暂节点退役不会删除已归档事实。

数据库触发器拒绝未复制完整源行及剩余确认时直接删除 outbox 源；尚未归档的旧代确认也
不能直接删除。当前代次的正常 checkpoint 确认压缩继续允许。源、确认、consumer 与历史表
不允许 TRUNCATE，以免绕过逐行检查和到期删除审计。

迁移不替部署方创建数据库角色。正常 Relay 角色需要对 `control_outbox_archive` 的
`event_id`、`database_epoch`、`batch_epoch`、`reason` 列有 SELECT 权限，用于核对迟到确认和
当前代次的确认压缩；不需要读取归档 payload 或 `control_event_ack_archive`。归档/删除角色
还需要相应源表、历史表和审计写入权限。权限不足时操作失败并回滚。应使用独立受控角色与
数据库访问审计，不把这些表授予 PUBLIC 或暴露给应用客户端。

归档获取独占事务级屏障；consumer 登记、确认、释放与短暂节点清理取得共享屏障，避免在筛选
和移动之间丢失新节点或确认。数据库启动触发器还在等待屏障后重新捕获新 consumer 的
coverage 和当前代次，覆盖旧 INSERT 路径。消费者续租与待处理读取不依赖屏障；归档调用自身
使用一秒 context。它仍会消耗数据库查询/写入资源，该期限不是目标负载下的性能承诺。

同代事件归档后，仍合法的迟到重复确认可识别已归档事实并幂等返回；未知 ID 和旧代次事实
不会被当作当前确认。所有 Relay 节点应先升级到支持迁移 022 的版本，再运行归档，避免旧
进程缺少迟到确认处理。不要将生产节点回滚到不理解这些历史的版本。

## 管理命令与保留期

先完成常规受控迁移、备份和节点升级。以下命令仅由具备相应数据库权限的运维角色显式执行，
不会自动部署或定时运行；服务二进制的构建步骤见[恢复流程](database-recovery.md)。
`REMOTE_DATABASE_URL` 通过受控环境注入，不放在命令行参数中；
`REMOTE_DATABASE_EPOCH` 必须是保存在数据库备份之外、已经核对的当前部署代次，即使初始代次
也要显式设置。批次 UUID 由操作方生成并保存：

```sh
export REMOTE_DATABASE_EPOCH='<当前部署代次 UUID>'
.local/remote archive control \
  --batch-id '<本批唯一 UUID>' \
  --expected-epoch "$REMOTE_DATABASE_EPOCH" \
  --limit 64 \
  --retention-years 1
```

输出只有批次 ID、代次、限制、cutoff、归档/保留时间及数量，不返回事件 payload、节点列表
或数据库地址。输出丢失/commit 结果不明时，使用**同一批次 UUID 和相同参数**重试；它返回
原结果，不再次选择事件。改变参数会冲突。空批次也被记录；以后要选择新到期事件，应使用
新的批次 UUID。若数据库之后经过恢复并更换代次，应按恢复记录核对旧批次；不能把旧批次 UUID
绑定到新代次以删除新历史。

保留年数为 1–10 年，默认从归档时起至少一年；年限按 UTC 日历计算，不依赖数据库会话时区。
更长组织要求应在归档前选择不短于适用要求的
全局批次期限；当前没有按组织自动选择策略或为已归档批次追加法律保全的接口。批次及源/确认
内容不可修改，未达到保留期的源行不可删除，确认不能单独删除。到期后由有权限的数据库角色
显式删除源历史时，确认随父行删除，`control.archive.delete` 同事务记录有效数据库角色、
登录数据库角色和固定 ID；
审计失败或恢复隔离时删除失败。这里没有自动删除调度，也不替代外部备份或法律保全流程。

批次结果永久保留用于操作 UUID 对账。迁移 022 在已有批次、历史或任何恢复记录时拒绝 down；
需要变更时使用审阅后的前向迁移。不要直接清空 outbox、确认或 proof 表来绕过恢复。数据库
超级用户仍能绕过普通 ACL/触发器，生产操作权限、职责分离和数据保全需要部署侧配置。

## 本地验证

隔离 PostgreSQL / race 用例覆盖独立节点确认、离线稳定节点、延迟提交与启动屏障、旧 SQL
登记路径、不同批次/重复 UUID、批量上限、延迟 commit 审计失败回滚、较长保留期、不可变
历史与到期删除审计。真实跨集群 `pg_dump` / `pg_restore` 后重新隔离/释放，验证旧代事件和
仍存在的确认完整保留，短暂节点不会提前级联删除旧确认，新代次使用自身快照。

实际生产二进制的 CLI 用例验证输出失败后原 UUID 对账，以及两个生产 Relay 进程在线时移动
一个双方已覆盖的旧事件，原连接和新的 subscription 仍可用。没有执行生产归档；本地身份、
模型及服务使用夹具，没有运行大负载、真机或厂商推送配置。
