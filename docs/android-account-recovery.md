# Android account checkpoint and refresh foundation

The foreground application now uses encrypted account checkpoints to restore its original device identity, revalidate access credentials, rotate DPoP refresh tokens and recover interrupted enrollment. Account restoration is verified through the actual controller, HTTPS fixture endpoints and AndroidKeyStore. Real school registration, an operating-system process-kill/restore exercise, target physical devices and the complete M1/M2 workflow remain acceptance gates.

`AccountVault` stores one bounded account slot under `Context.noBackupFilesDir`. A separate non-exportable AndroidKeyStore AES-256 key encrypts the payload with platform AES/GCM/NoPadding, a new provider-generated 96-bit IV and a 128-bit tag for every write. Domain/version, local random account UUID, organization UUID, deployment fingerprint and revision are authenticated as AAD. Only that public metadata and the ciphertext/IV are in the outer JSON. Approval/proof private keys use their existing independent aliases. No plaintext staging file or backup is created.

Vault reads/writes require a secure, currently unlocked device. API 35+ also sets `setUnlockedDeviceRequired`; API 26–34 use the explicit Keyguard gate because Android documents issues with that flag on older releases. This is not a claim of physical hardware enforcement on API 26–34 or remote attestation. Missing keys, damaged ciphertext, invalid metadata and mismatched account/deployment writes fail without silently regenerating an existing account's key. The payload limit is 95 KiB and the strict envelope remains within the shared 128 KiB JSON budget. Errors contain fixed codes without tokens or parser causes.

Writes use `AtomicFile`, explicit file and directory sync, and a checked readback. An expected revision fences cooperating stale writers within one app process; the revision itself is authenticated. This is not a hardware monotonic counter or protection against restoring an entire old file on a compromised OS. Local clear destroys that slot's AES aliases before removing the encrypted files. It does not revoke a remote device or log out the school account.

`LoginSession.authenticatedStorageBytes` serializes the credential pair and verified identity context for AEAD only. `StoredLogin.parseAuthenticated` must receive authenticated plaintext, the current deployment and the loaded proof-key thumbprint. Parsed credentials cannot authorize resource API calls. `TokenVerifier.revalidateStored` independently verifies the current access JWT, its signed expiry/scopes, purpose, issuer, subject, audience, client and DPoP binding before returning a usable session. The controller then checks `/v1/me`, the stored internal user UUID, current configured-organization membership and the original device/key version before exposing the authorized directory. It does not use the public deployment UUID or an OIDC subject as internal user authority.

Refresh uses only validated Discovery endpoints, `grant_type=refresh_token`, public client ID, resource and a DPoP proof without `ath` or access-token authorization. Issuer and resource-server nonce state stay separate. One defined `use_dpop_nonce` challenge may retry with a new proof JTI; other failures do not replay the request. One session instance can consume its refresh credential only once. An invalid grant requires fresh authorization. A successful response can rotate the refresh token; omission retains the existing one. The new access token must pass full signature/purpose/identity/scope/DPoP validation, cannot expand the previous access scopes and is bounded by both signed expiry and the response lifetime.

An ID token is optional in a refresh response. A returned ID token must preserve the original issuer, subject and audience set, keep any returned authentication time tied to the original login, preserve a returned nonce/authorized party, pass fresh issue/expiry validation and bind an optional `at_hash` to the new access token. A code hash is rejected because there is no new authorization code. Issuer signing-key rotation does not require the old issuer key to remain in JWKS when verifying a newly signed refresh response; the original identity baseline came from authenticated local storage.

`AccountCheckpoint` records the authoritative service user UUID, local key scope, proof/approval thumbprints, original device name and enrollment state (`pending`, `registering`, `active`) separately from credential state (`ready`, `refreshing`, `reauthenticate`). It retains unknown enrollment effects and the original name for an exact retry. A previously accepted device cannot become a fresh registration merely because a later lookup is absent. A `refreshing` checkpoint cannot begin another refresh. Cached-access validation cannot clear that marker: the library distinguishes newly verified browser authorization, refresh verification, cached-access verification and unvalidated stored credentials.

The application performs this sequence under an account-generation check and a shared persistence/cleanup lock:

1. Recover the encrypted record and exact platform key handles before cleaning other pending-key scopes. Match its public envelope to the authenticated inner account/configuration and current `/v1/me` user/organization mapping. A valid record protects its exact key scope while abandoned scopes are cleaned. Missing/invalidated keys or changed deployment configuration require explicit recovery/reset; enrolled keys are not replaced silently.
2. Before sending a registration POST, persist `registering`. After an ambiguous response/restart, query the original keys; preserve unknown state while offline and persist the accepted device before exposing the directory.
3. Before sending a refresh token, persist `refreshing` with the expected vault revision. Verify the response and persist the rotated credentials before resuming resource traffic. A crash/lost response leaves an uncertain marker that requires a new browser authorization with the retained proof key; do not retry the old rotating credential.
4. Keep the accepted device/key identity for reauthentication. A different browser subject is rejected before probing remote account metadata. A changed internal user ID or lost organization/device authority clears the local account. Local logout fences old browser/network/biometric callbacks, closes key owners, then serializes vault/key cleanup. The signed-out screen is exposed only after cleanup succeeds; an error offers a distinct cleanup retry. Account switching starts with this explicit local exit.
5. Renew credentials before expiry and before starting registration/directory operations with short remaining validity. A renewal cancels the old crypto prompt and retires its attempt ID before changing token context. The UI distinguishes recovery, locked/storage failure, renewal, retained-account reauthentication, ambiguous enrollment and cleanup. No pending browser verifier/state/code belongs in the persistent account record. A new phone without a secure lock can open login and reach security setup, but cannot POST enrollment before an encrypted checkpoint is saved.

On 2026-10-24 the shared foundation passed the full Gradle check, Android lint, app/test-APK builds and all 23 JVM tests. These checks passed again for the application integration on 2026-10-25. Five new auth tests exercise encrypted-storage payload round trips, denial until cached-JWT revalidation, issuer-key rotation, optional refresh ID tokens, original identity/auth-time binding, scope/downgrade/clock denial and unknown-effect checkpoint transitions. The real local HTTPS fixture checks refresh form/proof/nonce separation, the single defined challenge retry, credential consumption and invalid-grant denial.

Three explicitly enabled vault tests passed without skips on the task's fresh AOSP API 26 emulator with a fixture PIN. They verified non-exportability, fresh IVs/ciphertexts, no plaintext marker on disk, new-owner reads, tamper/tag/metadata/revision rejection, bounded/truncated input, missing-key denial without replacement, stale revisions, account replacement requiring clear, and recovery of the last checkpoint after an abandoned atomic write. The reused emulator initially had no GateKeeper service and failed the secure-lock fixture precondition; its owned test data was reset and the successful run used a working service and explicit fixture PIN. No other device or system PostgreSQL was modified. Modern Android branches, physical devices, platform lock/biometric changes, operating-system process death, encrypted message/cache storage and real school configuration remain separate gates.

On 2026-10-25 all 16 application instrumentation tests passed without skips on a fresh, owned API 26 AVD: eight controller recovery tests, seven Compose UI tests and one real Hilt application startup test. The controller tests exercise actual HTTPS/DPoP requests, the real encrypted vault and platform keys. They cover accepted registration recovery without another POST, cleanup of an abandoned proof key while preserving the authenticated scope, successful refresh rotation followed by another owner using the rotated credential, lost rotation responses, a persisted in-flight refresh marker, wrong-account reauthentication denial, internal-user/organization changes, logout during a delayed refresh response, and a real biometric registration signature with a lost POST response followed by recovery using the original keys. UI tests cover the distinct retry/reauthentication/exit actions and preserving the exact original enrollment name.

The HTTPS endpoints and issuer credentials in this instrumentation suite are test APK fixtures. Their generated CA trust and the private-client construction used for the fixture stay in test sources; the production HTTP factory continues using system TLS verification. Reopening a new controller after disposing the previous owner proves the actual account/crypto/network component restoration path, not an operating-system kill/restore or real Go/DSH/school login chain. The final expanded run used one software CPU core with Vulkan disabled. An earlier expanded run timed out during biometric registration and its two-core emulator later reported CPU-thread hangs and a segmentation fault; restarting its data also left GateKeeper unavailable. Only the owned AVD was reset, and the final fresh run preserved all protocol expiry checks. The test foreground host is opened before preparing the short-lived registration proof, matching the production interaction order. A transient FIR crash in Android-test lint passed on a focused rerun and subsequent full check; no lint rules were disabled.

Run the application suite on an explicitly prepared secure, unlocked device with a strong biometric enrolled. Confirm its one test enrollment prompt manually, or use only an owned emulator's sensor controls while that exact opted-in fixture reports readiness:

```sh
cd android
ANDROID_SERIAL=<test-serial> ./gradlew :app:connectedDebugAndroidTest -PaccountFixture=true
```

Run the vault tests on an explicitly prepared, secure, unlocked test device:

```sh
cd android
ANDROID_SERIAL=<test-serial> ./gradlew :core:keystore:connectedDebugAndroidTest -PvaultFixture=true \
  -Pandroid.testInstrumentationRunnerArguments.class=cn.edu.ustc.dsh.keystore.AccountVaultTest
```

The test opt-in checks the lock; it does not configure one, unlock a real device, enroll biometrics or authorize unrelated prompts. The fixture PIN belongs only to this task's disposable emulator.
