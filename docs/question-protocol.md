# Blocking questions over Relay

Both peers negotiate `question.blocking.v1`, alongside `session.read.v1` for viewing and `command.relay.v1` for answering. This capability covers native blocking questions and plan-review presentation. The separate [timed-question protocol](timed-question-protocol.md) connects native claims, `continued` state and late replies through `question.timed.v1`. Timed requests never become blocking requests. Question answers never create a tool approval token.

When both peers support questions, Relay adds `questions: true` to the host's `session.subscribe` payload. The host sends a `question.snapshot` after the initial session snapshot/checkpoint and whenever pending questions change. It carries the same request/runtime/epoch/session/subscription/sync identity as that session stream, with payload `{revision, items}`. Each item has an opaque `question_id`, `expires_at` and projected questions, including option labels/descriptions, optional free-text detail, multi-select and plan-review intent. Native call IDs, Agent references and unrecognized fields are excluded. Only the plugin's ordinary question requests enter this projection; tool approvals do not.

Each snapshot replaces the pending list for that sync. Revisions are monotonic within the router lifetime and may skip because other sessions changed or updates were coalesced. They are not native event sequence positions or persistence acknowledgements. Reconnect uses a new subscription/sync and starts from the current pending list. Runtime/epoch replacement invalidates old questions. Answer, timeout, cancellation, Agent disposal and unload remove the request and publish a replacement list. Releasing a follower or losing a phone socket does not itself answer a blocking question. The configured host interaction timeout still applies.

The router holds at most 64 pending interactions, projects at most 32 questions/options per batch, limits a question batch to 128 KiB and pending question data across the router to 1 MiB. Question snapshots use the existing 2 MiB fragmented-content limit and host queue budgets. Native follower reads and question notices are merged with at most one pending notice, so a quiet Agent can publish a new question without producing another native event. Relay checks current `session.read` and resource scope for every question frame, including fragments. Old peers receive no question frames.

The phone sends `question.answer` with request/runtime/epoch/session UUIDs and payload `{question_id, answers}`. Answers contain `id`, `selected` option labels and optional `custom` text. The complete frame must fit 64 KiB. Relay requires explicit `question.answer` in ticket/current grant and session/workspace scope, current device/key/grant and current host epoch. It rejects caller-supplied routing identity/digests, extra fields, duplicate answer IDs/selected labels and malformed batches. Viewing a question with `session.read` does not grant permission to answer it.

The canonical digest is SHA-256 of JCS over `{type, runtime_epoch, session_id, payload}`. Relay attaches authenticated user/device IDs; the host verifies digest and epoch, persists the encrypted command, and reports `host_accepted` → `dispatching` → `settled` or a rejection/unknown outcome. Native validation requires one complete answer per current question, known labels and valid selection cardinality; blocking free-text answers must be nonempty when no label is selected. The answer targets an exact ordinary question in that session. A question UUID cannot be used to answer a tool approval.

Consumption is synchronous and one-use across local and remote answerers. Competing devices produce one accepted answer; later answers are stale. Matching command retries return the durable result without consuming again; changed answers/epoch conflict. A host crash during ambiguous dispatch reports `outcome_unknown` and never recreates a callback. `settled` acknowledges that the answer was consumed and the command result was persisted; the native tool/turn result and checkpoint follow separately. Invalid or stale answers have a rejected receipt and leave other subscriptions connected.

The shared WSS Schema and goldens cover snapshots and Unicode answer digests. Host tests cover scoped streaming, plan intent, expiry, listener cleanup, one-use answers, durable retry, epoch binding and the inability to answer approvals. Go tests cover capability/action/resource denial, stale epochs, malformed batches, correlation and scoped receipts. `npm run test:remote-dsh` uses the production Go entrypoint, isolated PostgreSQL and installed npm DSH 0.2.1-rc.2: it prompts the native question tool, rejects an invalid label, races two registered devices, verifies exactly one settled answer, retries it, observes the question list clear and the native turn finish, and checks that question/answer bodies are absent from the database dump.

These are local identity/model/key-provider fixtures. The [Android question forms](android-questions.md) now render current typed questions and plans, validate complete replies, retain context-bound encrypted intent and reconcile one-use answer status. Production identity/key provisioning, physical-device acceptance, signed tool-approval UI, notifications and load/failure acceptance remain open.
