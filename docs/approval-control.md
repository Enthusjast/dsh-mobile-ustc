# Transactional approval control

The Go store implements authenticated host registration and owner-only signed decision acceptance. `store.NewApprovalControl` takes a fixed policy version, required assurance profile/maximum authentication age, and a trusted `auth.AssuranceVerifier`. The policy and mappings are deployment inputs. There is no default identity/MFA mapping or inferred assurance order. Changing a mapping requires a new policy version. This module has no public HTTP/WSS route yet. A separate [signed lease provider](approval-leases.md) now supplies current, bounded authority proofs; the host still has to durably consume one execution.

`Register` takes a server-authenticated installation connection/key version and a transient full context. It validates the shared binding contract, exact policy/assurance requirements, active host/installation/runtime, epoch, connection/key ownership, protocol, heartbeat within 45 seconds, and the available/running session's native/mobile/workspace mapping. A runtime row lock serializes the 64-active-request limit. Approval IDs cannot change their canonical context. Execution IDs and nonce hashes are unique per runtime across epochs, including terminal tombstones. No retention worker deletes them.

PostgreSQL migration 006 extends the existing approvals table with versioned metadata. New requests persist routing UUIDs, connection/workspace identity, binding and nonce digests, policy/assurance requirements, deadlines and state. Full contexts, tool arguments, workspace paths/resource facts, native call IDs and unsigned raw nonces are not stored. Accepted compact JWS proofs contain the signed decision's nonce and digest, as required for audit, but contain no tool arguments. Public device keys remain in the device registry. Audit/outbox entries contain only fixed status metadata and hashes.

`Decide` requires the principal already established by JWT/DPoP verification and the exact admitted socket ticket. It checks that their proof key agrees, and locks current user/device/membership/host/installation/runtime/session/owner-grant facts. The registered approval key/version must match the signed user/device claims. Both the ticket and current grant must contain `approval.decide` and the target session/workspace, and the ticket must remain a subset of the current grant. An operator action entry or organization membership does not satisfy the owner requirement. Authentication assurance and token/grant/decision/request expiry are checked against the database clock after locks; final compare-and-set checks deadlines again. Admission has a 1.5-second cancellation deadline.

Signature verification uses the shared canonical ES256 contract and the registered key, then atomically records one canonical payload digest, signed proof, verified authentication time/token expiry, device/key/grant versions and decision. Invalid signatures, changed context, missing/unmapped assurance, revoked resources, failed writes or an ignored compare-and-set consume nothing. Identical canonical decisions, including equivalent ECDSA signature encodings, retry idempotently while their proof and current authority remain valid. Another actor or choice conflicts. A retry cannot refresh the original recorded token/assurance evidence or grant version.

Allow decisions become `decision_received`; reject decisions become `denied`. Neither a service acceptance receipt nor an outbox event proves native execution. The metadata update, audit and outbox insertion commit together. Any failure rolls the entire admission back. The [lease provider](approval-leases.md) rechecks the recorded actor/key/grant/policy/assurance and deadlines, issues a bounded signed lease, and lets the host independently verify and durably consume it before native execution.

Connection replacement, including reuse of the same epoch, ends old requests in the attach transaction. A current detach does the same; stale detach cannot affect a newer connection. Pending requests become `invalidated`; previously received allow decisions become `outcome_unknown`, since the service does not know whether the host consumed them. Expired active requests are ended during the next successful registration: pending becomes `expired`, received allow becomes unknown, and each transition writes audit/outbox facts. There is no periodic expiry delivery worker yet. The existing control worker deliberately leaves `approval.pending`, `approval.decided` and `approval.ended` topics pending until an approval delivery/reconciliation consumer is implemented.

Legacy rows remain metadata version zero and are never accepted by the new controller. Upgrade invalidates old pending rows and marks legacy received decisions unknown. Rollback retains proofs/audits and maps active/unknown rows to the nonexecutable legacy `invalidated` state; it never restores pending execution. Re-upgrade does not recreate a valid binding.

Run `npm run test:remote-dsh`. Its disposable socket-only PostgreSQL cluster now also runs the full Go suite with race detection and cache disabled, so PostgreSQL approval tests cannot silently skip. Each Go test uses its own temporary database. Coverage includes unregistered/altered contexts, all current authority checks, multiple devices racing, high-S retries, audit/outbox/ignored-update failures, bounded locking, token/grant expiry while waiting, request cleanup, concurrency limits, reconnect/detach and migration rollback/re-upgrade. The existing production Go + real npm DSH 0.2.1-rc.2 session/question chain also runs, with local identity/model fixtures. These are separate evidence: signed approval WSS/host callback integration, real school IdP step-up, Android signing and production key/lease providers remain to be implemented.
