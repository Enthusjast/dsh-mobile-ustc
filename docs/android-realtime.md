# Android authenticated Relay transport

The Android shared modules now issue read-scoped realtime tickets and establish the existing Relay v1 device connection over TLS. They validate socket challenges, sign with the registered device proof key and verify the accepted device/runtime/grant/scope/lease. This is the transport foundation: the foreground application still shows the authorized runtime directory. Session subscriptions, 2 MiB logical payload reassembly, snapshot/event/assistant merging, history, foreground heartbeat ownership, fresh-ticket reconnect and account-bound connection cleanup are the next integration work. M1/M2 have not passed their complete exit gates.

`RemoteApi.readTicket` posts the explicit runtime and `session.read` scope through the existing DPoP resource client. The request uses a fresh proof, access-token hash and resource nonce. One middleware `use_dpop_nonce` challenge can retry before admission with a new proof JTI; ordinary write/network failures are not replayed. The response must match the requested runtime and exact literal scope, have a valid grant version and contain a fresh canonical 256-bit token. A ticket object is single-use even after failed upgrade. Its raw value stays out of URLs, UI state, persistence and error text.

Scope selection follows the authenticated directory: prefer a session explicitly present in the grant, otherwise its returned workspace must be present in the workspace grant. `session.list` does not imply body read. The client does not manufacture a workspace or convert a workspace grant into a literal session grant. Service ticket issuance and each read still recheck current authority independently.

The fixed endpoint is the configured HTTPS origin's `/v1/realtime`, using `Authorization: DSH-Ticket` and `Sec-WebSocket-Protocol: dsh.remote.v1`. TLS uses the standard platform provider, the HTTP client's trust/hostname/pin policy and its TLS 1.2/1.3 cipher policy. The current connector opens a direct socket and rejects a selected HTTP/SOCKS proxy before connecting instead of bypassing it; proxy tunneling, HTTP/2 extended CONNECT, certificate-rotation deployment and target-network acceptance remain gates. Redirects, cookies and negotiated WebSocket extensions/compression are not used.

The narrow RFC 6455 text adapter checks the HTTP upgrade/accept key and subprotocol with a 16 KiB header budget. Server frame lengths are checked before payload allocation; both an individual frame and a complete text message are limited to 64 KiB. Server masking, reserved bits/opcodes, nonminimal lengths, invalid control/close frames and malformed UTF-8/JSON are rejected. Up to 64 RFC fragments may compose a message within five seconds; UTF-8 is decoded only after complete byte reassembly so a scalar may cross fragment boundaries. This is separate from the application's `session.fragment` logical-content protocol, which is not implemented yet. Input is limited to 200 frames/second. Reads apply TCP backpressure without an unbounded incoming queue; up to eight bounded writes are admitted, serialized and subject to a five-second write deadline. Cancellation closes the underlying TCP/TLS socket to interrupt blocking I/O. Protocol framing and broader hostile-peer/network behavior still require production security/load review.

The device hello advertises only `connection.heartbeat.v1` and `session.read.v1`. Its digest uses the same normalized, length-prefixed encoding as Go/TypeScript. `contracts/security/relay-device-hello.json` is a public-only shared vector consumed by all three languages. The ES256 `dsh-relay-handshake-proof+jwt` binds device issuer, fixed realtime audience, current challenge/connection/nonce, runtime, normalized hello digest, issue time and a fresh proof JTI. It contains no caller-supplied JWK or desktop credential. The proof signer independently verifies its provider's signature against the loaded public key.

`hello.ok` must preserve connection/device/runtime identity, grant version and ticket scope, select only requested capabilities, and keep protocol/frame/heartbeat settings within v1. Server time and the five-minute lease are bounded; resource use is further constrained by the original access-token deadline and monotonic elapsed time. Receiving checks lease validity before and after delivery. Application readers must own periodic ping/pong handling, connection disposal and fresh-ticket reconnection; authenticated transport alone does not mean a snapshot has synchronized.

On 2026-10-25, JVM protocol/network tests and full Gradle lint/APK checks passed. Tests exercise the shared digest, exact scope/role/identity/capability/lease denial, canonical nonce and RFC 3339 precision, real HTTPS ticket issuance with one nonce challenge, TLS upgrade and key verification, credential reuse denial, redirect/subprotocol substitution, fragmented Unicode with interleaved ping/pong, header controls, 64 KiB boundaries, overlarge advertised lengths before payload reads, binary/masked/truncated/invalid frames, continuation floods, close UTF-8 and cancellation. A deterministic 4,096-header corpus also checks bounded parsing and rejection behavior. These tests are targeted evidence, not a general-purpose WebSocket or production-security certification.

The final shared suite contains 42 passing JVM tests without skips; `npm run verify` passed all 168 host tests and contract/build/type checks. Android lint and debug app/test-APK assembly passed with `./gradlew --max-workers=1 check :app:assembleDebug :app:assembleDebugAndroidTest`. A repeat of the known FIR analysis crash on Android test sources required a serialized rerun; no lint checks were disabled. Caller cancellation remains cancellation, while an expired transport/fragment deadline becomes a stable Relay failure for the future reconnect owner.

The selected API 26 instrumentation test passed using an actual non-exportable AndroidKeyStore proof key, a fixture HTTPS resource endpoint and a fixture TLS Relay. The server independently verifies the returned proof and hello digest; a second connect with the same ticket fails locally. The fixture issuer, CA and peer exist only in test sources. Run it on an explicitly selected device:

```sh
cd android
ANDROID_SERIAL=<test-serial> ./gradlew :app:connectedDebugAndroidTest -PnetworkFixture=true \
  -Pandroid.testInstrumentationRunnerArguments.class=cn.edu.ustc.dsh.mobile.RelayKeystoreTest
```

`npm run test:remote-kotlin` adds an actual Kotlin/Go/PostgreSQL composition to the disposable-cluster runner. It builds the SDK-free JVM probe, generates an ephemeral issuer/proof-key fixture in a private 0600 file, independently verifies its signed resource token, obtains a real service ticket, completes the real Go Relay challenge, exchanges a heartbeat and checks a correlated scoped read's `runtime.offline` reply without a host. It then runs the separate real npm DSH 0.2.1-rc.2 chain. These are complementary compositions; the command does not yet route DSH session content into the Android UI or validate real school login. The test probe is absent from production artifacts, uses only generated local credentials and shuts down its owned HTTP resources before exiting. The existing `test:remote-dsh` path remains independent of a JDK; its optional Kotlin composition test explicitly skips unless enabled by the new command.

The combined command passed with Go race detection and private PostgreSQL databases. The first probe attempt correctly rejected a fixture deadline that extended beyond the signed JWT's second precision; the fixture was corrected without changing token policy. A later successful protocol exchange exposed a fixture-process HTTP-executor cleanup issue, which was corrected before the passing run. System PostgreSQL, school identity and other devices were not modified.

During a later parallel verification, the existing approval-detail cancellation test reached its two-second read deadline while the software Android emulator was active. It passed 20 focused race repetitions after the owned emulator was shut down; the final complete composition was rerun serially without changing any timeout. The platform and combined-service runs remain separate evidence scopes.

The framing/upgrade follows [RFC 6455](https://www.rfc-editor.org/rfc/rfc6455.html). Resource and device possession proofs retain the existing [authentication contract](m1-authentication.md); subscription identities and content semantics remain in the [session read protocol](session-read-protocol.md).
