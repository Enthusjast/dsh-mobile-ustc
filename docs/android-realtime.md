# Android foreground session reader

The Android application now opens the authorized runtime's session directory and reads a selected session through the existing TLS Relay. The shared reader owns subscriptions, bounded logical reassembly, snapshots, native events, assistant attempts, history, heartbeat and fresh-ticket reconnection. The foreground UI shows connection, persistence, paging and offline states and supports collapsible reasoning. The [encrypted outbox and foreground composer](android-command-delivery.md) add queue/steer text, explicit retry and epoch-bound cancellation on the same connection. [Phone binding](android-host-binding.md) is also implemented. The [encrypted transcript cache](android-transcript-cache.md) persists confirmed history under fresh read authority. The [creation view](android-session-creation.md) uses its own foreground runtime connection and the same durable command coordinator. The [question forms](android-questions.md) handle ordinary plans and native timed claims/late replies. The [signed tool-approval view](android-approvals.md) reviews complete actions and owns per-use biometric signatures on the same session socket. The [owned API 26 APK/Go/DSH composition](android-device-composition.md) now validates a connected native-key path; session archive, real school identity and broad physical/network acceptance remain work. M1/M2 have not passed their complete exit gates. School identity configuration is unavailable; development continues with local fixtures as requested.

`RemoteApi.readTicket` posts the explicit runtime and `session.read` scope through the existing DPoP resource client. The request uses a fresh proof, access-token hash and resource nonce. One middleware `use_dpop_nonce` challenge can retry before admission with a new proof JTI; ordinary write/network failures are not replayed. The response must match the requested runtime and exact literal scope, have a valid grant version and contain a fresh canonical 256-bit token. A ticket object is single-use even after failed upgrade. Its raw value stays out of URLs, UI state, persistence and error text.

Scope selection follows the authenticated directory: prefer a session explicitly present in the grant, otherwise its returned workspace must be present in the workspace grant. `session.list` does not imply body read. The client does not manufacture a workspace or convert a workspace grant into a literal session grant. Service ticket issuance and each read still recheck current authority independently.

The fixed endpoint is the configured HTTPS origin's `/v1/realtime`, using `Authorization: DSH-Ticket` and `Sec-WebSocket-Protocol: dsh.remote.v1`. TLS uses the standard platform provider, the HTTP client's trust/hostname/pin policy and its TLS 1.2/1.3 cipher policy. The current connector opens a direct socket and rejects a selected HTTP/SOCKS proxy before connecting instead of bypassing it; proxy tunneling, HTTP/2 extended CONNECT, certificate-rotation deployment and target-network acceptance remain gates. Redirects, cookies and negotiated WebSocket extensions/compression are not used.

The narrow RFC 6455 text adapter checks the HTTP upgrade/accept key and subprotocol with a 16 KiB header budget. Server frame lengths are checked before payload allocation; both an individual frame and a complete text message are limited to 64 KiB. Server masking, reserved bits/opcodes, nonminimal lengths, invalid control/close frames and malformed UTF-8/JSON are rejected. Up to 64 RFC fragments may compose a message within five seconds; UTF-8 is decoded only after complete byte reassembly so a scalar may cross fragment boundaries. Input is limited to 200 frames/second. Reads apply TCP backpressure; the reader has a two-frame incoming channel and up to eight bounded serialized writes, each with a five-second deadline. Cancellation closes the underlying TCP/TLS socket to interrupt blocking I/O. Protocol framing and broader hostile-peer/network behavior still require production security/load review.

Application `session.fragment` groups are separate from RFC fragmentation. They retain one subscription/request/sync/content identity, accept 2–52 ordered canonical-base64 pieces of at most 40 KiB and publish only after complete UTF-8/JSON validation. Each logical payload is limited to 2 MiB, depth 32, 65,536 values and a ten-second reassembly deadline. The display parser does not change the existing 128 KiB signing/configuration parser. Retained history is limited to 4,096 native records and an 8 MiB conservative content-accounting budget; stream blocks/chunks/text also have explicit bounds. Reaching the history limit stops further paging; a snapshot that cannot fit triggers a smaller opening window or an explicit error.

`SessionWindow` preserves the opening cursor for all pages while native live events advance a separate observed cursor. Dense native positions and global assistant revisions/indices are checked; changed repeats and gaps require a replacement snapshot. Compact assistant baselines restore the stream before suffixes are applied. A known attempt's durable assistant event stays hidden until the matching committed end names its event type and native position. Abandonment discards the transient. Model-only surface replacements do not erase or duplicate the human transcript. The host projects explicit human input and answered native late-question replies, while other user-role producer context only advances the native cursor. Persistence checkpoints may lead observation and never move backward; a failed checkpoint remains visible as a warning.

Each physical reconnect obtains a fresh ticket, socket, subscription and replacement snapshot, with bounded jittered backoff. An offline host pauses content reads while the phone keeps its heartbeat/control connection for revocation. Manual retry obtains a fresh ticket/subscription; terminal states require a user retry. Ping/pong runs every 20 seconds. Pagination deadlines do not cancel socket reads, and only one correlated page is in flight. Logical fragment and held-settlement deadlines require resynchronization. A temporary memory-only cache contains confirmed durable display rows, excludes live attempts and held settlements, and expires with the previous connection lease using wall and monotonic time. It is cleared on epoch change, revocation, credential loss, backgrounding, account disposal or logout. The encrypted disk cache separately retains confirmed windows for up to 30 days under per-session and owner capacity bounds. After a new key-proved connection and exact-session read authorization verify the current workspace/grant mapping, it can supply history while the host is offline. Raw held settlements and their suffixes are excluded until their matching committed end. Epoch and scope changes purge affected data; queued writes cannot restore it after revocation. A disk cache never resumes an old subscription or grants offline authority, and actual OS-kill/power-loss behavior remains a separate gate.

The controller fences directory jobs and reader collectors by account and navigation generation. Leaving the foreground closes the reader; returning rechecks the session directory before opening a fresh connection. A narrower directory grant retires the old view. Resource-specific read revocation clears the body and reconciles current authority while retaining an otherwise authorized account. Directory-only access never enables reading, and absent/malformed access metadata fails closed. The UI distinguishes no messages from unavailable offline history and labels temporarily cached records separately.

Read-only device hello advertises `connection.heartbeat.v1`, `session.read.v1`, `question.blocking.v1` and `question.timed.v1`. Question display does not grant answer or timing-claim authority. An explicit command scope adds `command.relay.v1`, and cancellation additionally adds `session.cancel.v1`. The reader attaches command sending only after the correlated subscription snapshot is ready. Its digest uses the same normalized, length-prefixed encoding as Go/TypeScript. `contracts/security/relay-device-hello.json` is a public-only shared vector consumed by all three languages. The ES256 `dsh-relay-handshake-proof+jwt` binds device issuer, fixed realtime audience, current challenge/connection/nonce, runtime, normalized hello digest, issue time and a fresh proof JTI. It contains no caller-supplied JWK or desktop credential. The proof signer independently verifies its provider's signature against the loaded public key.

`hello.ok` must preserve connection/device/runtime identity, grant version and ticket scope, select only requested capabilities, and keep protocol/frame/heartbeat settings within v1. Server time and the five-minute lease are bounded; resource use is further constrained by the original access-token deadline and monotonic elapsed time. Receiving checks lease validity before and after delivery. The reader reports READY only after applying its correlated subscription snapshot.
