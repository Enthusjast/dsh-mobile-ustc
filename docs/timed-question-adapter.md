# Native timed-question adapter

The host now adapts the installed npm DSH 0.2.1-rc.2 `userQuestions` service. `InteractionRouter.timed` owns the adapter; the plugin explicitly requires `sessionProjections`, whose native `userQuestions` projection supplies continued/settled facts. This is a host implementation with native package tests. Relay/mobile timed-question transport is still pending and no timed capability is advertised on WSS.

On a managed, exact live root Agent, a timed request registers an opaque question UUID and waits on the native foreground lifetime. It has state `open` and no fabricated expiry before a UI claim. A claim drives native `attachWait`; the first frame supplies the native remaining duration, and the adapter caps its own timer by that duration without adding read/scheduling delay. The claim's abort signal releases the native claim. Final answer, native cancellation, expiry, Agent invalidation and unload release all claims. UI claims cannot keep the foreground callback alive indefinitely.

An answer during the foreground window synchronously consumes the pending callback once. Empty selections without custom text are valid submitted skips for timed questions, as defined by the native timed tool; they are not a timeout or permission. Ordinary blocking questions retain their existing answer rules. Tool approval maps and tokens are separate.

At timeout the original native `askTimed` returns `{pending: true, callId}`. The adapter does not infer that the old callback can still be completed: it waits for the native tool result/projection to establish `continued`. The same question UUID survives that transition within an adapter lifetime. Continued answers call native `userQuestions.answer`, which steers a `user-question-reply` user message. State is `reply_queued` until that native message is admitted; duplicate queued replies are refused. The native projection removes the question only when its reply is recorded. A discarded queued reply can become answerable again; future command/transport receipts must distinguish queue admission from observation.

Adapter reload discards callback identities and reconstructs only native `continued` questions, assigning fresh UUIDs. Old UUIDs cannot answer the new adapter. No restored database row or projection recreates an old tool callback. Agent invalidation also prevents a disposed Agent instance from reappearing through a late event. Only current live root Agents are eligible; cold-session resume and ownership remain governed by the current-process DSH controller.

Limits are 64 timed records and 1 MiB of projected question data per adapter, 128 KiB per batch, eight claims per question and 128 claims per adapter. Unprojectable/over-budget continued history is omitted without throwing into native event commits. Callers must abort and drain a claim iterator when its UI or transport ends. The blocking-question router retains its separate existing budgets.

`host/remote-control/tests/timed-questions.test.ts` uses the real installed DSH services/Agent/tool loop with a deterministic local model. Coverage includes foreground answer, unclaimed expiry, claim release, held-window expiry, native cancellation, unload, and a real timed `ask_user_question` invocation. After its timeout, reloading the adapter reconstructs continued state with a fresh UUID; answering emits exactly one native user message and never a second result for the old tool call. Invalid and competing replies are rejected. This is local native-runtime evidence, not school identity, Android or Relay timed-question acceptance.

Remaining transport work: a separately negotiated timed capability; scoped timed snapshots; connection/subscription-bound claim admission, remaining-time responses and teardown; epoch-bound answer commands; durable late-message checkpoint/receipt semantics; shared schemas/goldens; and combined Go/PostgreSQL/DSH/phone tests. The existing `question.blocking.v1` protocol carries blocking questions only.
