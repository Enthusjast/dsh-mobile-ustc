# 审计日志的数据库归档

迁移 `026_audit_history` 为审计日志增加不可变保护和显式管理命令。超过 90 × 24 小时的热表
记录可按批移动到同一 PostgreSQL 中受权限保护的历史表；原始记录、批次结果、源数据库代次和
归档审计在单个事务中保存。任何复制、删除、审计或提交失败均整体回滚。

这是数据库内的历史归档，不是独立加密冷备份。单条审批签名证据可另行[加密导出](approval-evidence-export.md)；
完整审计历史的外部导出、密钥托管、自动调度及生产恢复演练仍需完成，不要据此认定计划中的冷热保留要求已经全部落实。
管理命令不提供公网 API，不自动部署、归档或删除生产数据。

## 时间、来源与权限

迁移后，新审计行的时间和数据库代次由数据库在插入时写入，忽略调用方提供的值；因此热保留期
从数据库写入时间计算，而不是用事务提交顺序或调用方时间推断。数据库时钟必须保持同步。
迁移前的行可能跨越过备份恢复，无法可靠推断来源代次，归档后 `source_epoch` 保持 NULL，
不把它们标为初始代次。新记录保留写入时代次；数据库恢复后，旧来源代次不会被重新解释为
当前事务快照。

归档每批默认 64 条、最多 128 条，按时间和 ID 选择当前已提交的记录并跳过正被锁定的行。
时间与 ID 只用于选择，不是完整性水位；晚提交的旧记录仍会在后续批次被选中。每条源行的
JSON 形态最多 256 KiB，若选中更大的行则整批失败且不移动源；需由受控角色检查和处理，
不能靠静默跳过宣称保留完整。迁移创建时间索引，部署前应评估数据库迁移窗口和资源。

迁移不创建数据库角色。审计写入角色需要 SELECT 恢复状态表以取得当前代次，并保留原有
`audit_log` 插入及序列权限。归档角色还需要读取、锁定和删除热审计行，以及读取/插入
`audit_archive_batches` 和 `audit_log_archive`；PostgreSQL 行锁需要相应 UPDATE 权限，
可将 `audit_log` 的 UPDATE 限于 `id` 列、恢复状态表的 UPDATE 限于受约束的 `slot` 列；
触发器仍拒绝修改审计内容，归档角色不需要更改恢复代次的权限。归档角色也需写入 `audit_log`。
写入权限应限制到实际业务列，不应授予 `id` 列的 INSERT 或序列的 UPDATE 权限，以防手工重用旧 ID。
历史表未授予 PUBLIC，直接
读取和文件访问需由部署方的数据库/系统审计记录。源记录可能包含资源和身份元数据，应使用
独立受控角色；数据库超级用户仍可绕过普通 ACL 和触发器。

## 操作与保留

先按顺序应用迁移、核对节点、数据库时钟、备份和 ACL。二进制构建方式见[数据库恢复](database-recovery.md)。
以下命令在仓库根目录执行，数据库连接通过 `REMOTE_DATABASE_URL` 受控环境注入，代次在备份
之外保存并显式配置：

```sh
export REMOTE_DATABASE_EPOCH='<当前部署代次 UUID>'
.local/remote archive audit \
  --batch-id '<本批唯一 UUID>' \
  --expected-epoch "$REMOTE_DATABASE_EPOCH" \
  --limit 64 \
  --retention-years 1
```

输出仅含批次 ID、代次、数量和时间，不含源审计正文、身份、数据库连接或原始异常。命令在
同一事务中记录 `audit.archive.batch`，完成不可变复制并删除对应热行。输出丢失或结果不确定时，
用相同 UUID、参数及代次重试以取得原结果；参数改变或恢复后更换代次会产生冲突。空批次也有
记录，后续新到期或晚提交记录需要新的批次 UUID。

归档时间和截止时间由数据库确定，归档后的保留期为 1–10 个 UTC 日历年，默认至少一年。
该期限从本次归档起算。源热记录不能直接修改或删除，除非同事务存在完整、匹配且已审计的
归档副本；历史记录同样不可修改，未到期不可删除。到期后有权限的管理角色可显式删除历史行，
每条删除与 `audit.archive.delete` 同事务提交。批次标识永久保留供对账；没有自动清理或
追加法律保全接口，更长要求应在归档前选择并通过运维权限控制。迁移 026 在新增来源记录、
归档批次或恢复记录存在后拒绝 down，应使用经过审阅的前向迁移。

## 本地验证

隔离 PostgreSQL/race 用例覆盖时间/代次伪造拒绝、原行精确复制、幂等批次、并发重试、锁定行
与晚提交、大小上限、审计失败回滚、到期删除和权限限制，以及真实 `pg_dump` / `pg_restore`
后的未知来源与旧代次保留。实际服务二进制验证了输出丢失后的同 UUID 对账。没有运行生产
归档、大负载或真机测试。
