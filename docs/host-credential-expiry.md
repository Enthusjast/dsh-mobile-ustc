# Host 挑战与凭据签发的期限检查

Host 挑战创建和连接凭据交换在事务提交前使用 PostgreSQL `clock_timestamp()` 复核期限。
持有行锁只能固定权限和密钥版本，不能阻止时间流逝；SQL 中在等待行锁或触发器前求值的
期限条件，也不能代表等待结束后的时间。

创建挑战在审计写入后检查新挑战仍未到期，避免把已经失效的挑战作为成功结果返回。
交换在锁定挑战行后重新检查其期限；消费挑战、插入凭据和写入审计后，再检查原挑战和新
凭据的期限。此检查是签发决策点，数据库提交和网络应答可以随后完成，不以响应到达时间
作为挑战消费或凭据签发生效时间。

等待期间过期返回既有 HTTP 401 `host_credential.invalid`，不返回本次秘密。事务整体回滚，
不保留本次挑战消费、新凭据或成功审计。若只有本次生成的凭据到期，回滚后尚未过期的挑战
仍可配合有效证明重新交换一次；已经到期的挑战则必须重新申请。成功交换仍消费一次，
旧证明不能在同一挑战下产生第二条凭据。

数据库查询错误沿用服务不可用分类；只有 PostgreSQL 确认中止的事务按原预算重试，到期
拒绝不触发事务重试。签名验证、当前账号/安装/Host 状态、密钥版本、挑战及凭据数量限制
仍使用原有检查。数据库只保存秘密摘要，90 秒挑战与五分钟凭据的正常 TTL、协议格式和
数据库结构保持原样。

## 验证

真实隔离 PostgreSQL 测试先复现四种过期后仍成功的时序：创建挑战等待审计、交换等待审计
跨过挑战或新凭据期限、消费挑战的触发器等待跨过挑战期限。修复后均拒绝并核对回滚结果，
另保留等待挑战行锁跨过期限的拒绝用例。新凭据到期的失败交换还验证原挑战可重新交换，
且成功结果可用于既有凭据校验、不能再次消费。

测试只缩短夹具行的期限，不调整系统时钟或生产 TTL；真实锁等待经 PostgreSQL 活动视图
确认，再按数据库时钟等待到期。正常链路通过本机 npm DSH `0.2.1-rc.2`、双节点生产 Go
入口和本地身份/模型夹具单独回归。没有学校生产配置、Android APP、真机、大负载或厂商
推送配置验收。
