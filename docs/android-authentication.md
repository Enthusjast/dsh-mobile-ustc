# Android login and registration development slice

The repository now builds a Compose/Hilt development application with school-login configuration, browser authorization, independently verified OIDC/access tokens, DPoP HTTPS requests, biometric device registration and an authorized runtime directory. It is an initial foreground application, not the complete M1/M2 client or a release candidate. The real school's issuer/client/resource registration and end-to-end Go/DSH/Android login have not been verified.

`android/core/auth` owns a ten-minute, in-memory Authorization Code + PKCE transaction. State, nonce and verifier each use 32 random bytes; only S256 is sent. The fixed native redirect is `cn.edu.ustc.dsh.mobile:/oauth2redirect`, which must be registered exactly for the school's public client. The exported callback independently checks the URI, duplicate/escaped query names, scalar UTF-8, state and any required response issuer before accepting one authorization code. Invalid callbacks do not spend the pending attempt; cancellation, expiry or a clock rollback ends it. The app uses AppAuth 0.11.1 to construct the authorization request from validated Discovery endpoints and Custom Tabs for the browser. Verifier, code and tokens are not put in Intent extras, Compose state, SavedState or logs. Process death requires a new login.

Discovery must match the configured issuer and uses only explicitly allowed HTTPS endpoint origins. Advertised code, S256, public-client and ES256 DPoP capabilities must not contradict the requested flow. Missing optional capability metadata never selects a weaker request: the client still sends S256 and DPoP, and rejects a Bearer/unbound token response. The selected ID-token algorithms must be advertised; only configured RS256/ES256 algorithms are used. JWKS comes only from the validated URI and has bounded size/key count; token-supplied key URLs are not followed. Duplicate JSON members and private key material are rejected.

The client independently verifies ID-token and access-token signatures with Nimbus JOSE. It requires exact issuer, client/audience, subject agreement, nonce, time bounds and optional azp/at_hash/c_hash checks. The access token must have `at+jwt` purpose, client_id, jti, required resource scopes and `cnf.jkt` matching this phone's proof key. Its signed deadline and token-response lifetime both constrain use. Local biometrics do not supply school MFA/ACR; the service still applies its verified access-token assurance policy to sensitive actions.

`android/core/network` uses OkHttp 4.12.0 with HTTPS, bounded JSON responses, finite deadlines, cancellation, no disk cache/cookies and disabled redirects/implicit retries. The app never sends an access token on Discovery/JWKS/token calls. IdP token-endpoint and resource-server nonces are separate. A defined `use_dpop_nonce` challenge permits one retry with a new JTI. Token requests contain PKCE/resource parameters and a DPoP proof without ath; resource requests use `Authorization: DPoP`, the matching ath and the actual normalized method/URL without query/fragment. Nonce use is serialized per resource client. Ordinary network failures do not automatically replay code exchanges or writes.

Registration first obtains a current `/v1/me` response and nonce. This authenticated response must include the internal service user UUID and current organization memberships; the client checks exact issuer/subject/client/scopes, rejects duplicate or unknown roles and requires membership in its configured organization. It retains a stable internal mapping within the session and rechecks it before registration preparation and directory refresh; a changed user mapping or lost organization ends the local session. Membership alone never supplies runtime grants. The app prepares an approval-key possession proof bound to verified issuer/subject, both distinct key thumbprints, trimmed UTF-8 device-name digest and one reserved DPoP JTI. A real BiometricPrompt CryptoObject authorizes that exact platform approval-key operation. The request's DPoP proof uses the same JTI when posting the signed proof/public keys to `/v1/devices`. There is no automatic registration retry: changing the DPoP JTI requires a new approval-key proof and explicit local authentication, and a lost write response triggers a read-only current-key lookup. A failed lookup leaves an explicit status-query state; a matching accepted key resumes the directory, and a confirmed absence allows a fresh explicit registration. Matching server-side retries converge on one device and audit record, including when the original insertion is still settling. See [enrollment reconciliation](device-enrollment-recovery.md). The typed response must contain a valid device UUID and version 1 before the app reads the runtime directory.

The account controller uses generation checks, distinct biometric attempt IDs, exact crypto-object matching, cancellation and closed key handles to fence late browser/network/biometric continuations. Token expiry and explicit authority-loss responses clear the local session and directory. Public pending-key scope IDs are committed before creating platform keys so interrupted enrollment keys can be cleaned up after process death. This ledger stores no identity token, subject, verifier, state, code or refresh token. Sessions currently remain in memory. Local exit closes handles and clears this local session; it does not claim service-side device revocation or school-wide logout. Server-side device cleanup, durable accepted-device recovery, encrypted token persistence and refresh/account restoration remain work.

The UI uses Material 3 semantic colors, system fonts, lifecycle-aware state collection, scrollable phone layouts and explicit loading/cancellation/error states. A missing/invalid school deployment disables login; the application ships no default identity service or fabricated runtime list. A valid configuration is validated by the shared public schema, canonicalized and copied into generated APK assets only when explicitly supplied at build time; secret/unknown fields are rejected before packaging. A subsequent unconfigured build removes an earlier build's asset. Screen capture and application backup/device-transfer extraction are disabled for the live application; UI test captures contain synthetic public state in a test host only.

Build the unconfigured development APK:

```sh
cd android
./gradlew check :app:assembleDebug
```

Its output is `android/app/build/outputs/apk/debug/app-debug.apk`. Install it on a selected development device with `adb -s <test-serial> install -r ...`. The default screen asks for a school-configured installation; it does not attempt any network login.

For a configured development build, copy `deploy/android/deployment.example.json` outside the source tree, replace every example value with the verified school/remote-service registration and build:

```sh
./gradlew :app:assembleDebug -PdeploymentConfig=/absolute/path/to/verified-public-deployment.json
```

The file contains public deployment values only: never client secrets, passwords, tokens, private keys or desktop model credentials. `organization_id` identifies the configured organization; UUID syntax/local namespacing alone is not membership authority. `resource` must be the IdP's registered remote resource indicator, `audience` must match the service and `endpoint_origins` must explicitly include every discovered authorization/token/JWKS origin. TLS verification remains enabled. The custom scheme callback still needs native-client registration and the usual package/domain ownership review; verified App Links remain a deployment option to implement and validate.

On 2026-10-24, `./gradlew check :app:assembleDebug :app:assembleDebugAndroidTest` passed for the initial APK, including Android lint and all 16 JVM tests. The subsequent authoritative-account slice passed `./gradlew check :app:assembleDebug` with 18 JVM tests (six protocol, five crypto, three login, two HTTPS and two account-mapping tests; no skips). JVM tests use generated ES256/RS256 issuer keys and real local HTTPS/MockWebServer calls to verify PKCE, identity/nonce/audience/purpose/scope/key-binding denial, nonce separation/retry, resource proof hashes, registration proof/JTI binding, once-only submission, request cancellation, redirects and response limits. Account tests reject missing/changed internal identities, absent organizations and malformed/duplicate roles before an enrollment write. A transient FIR resolution failure in Android-test lint passed on a focused rerun and the subsequent full check; no lint checks were disabled.

The isolated API 26 emulator passed all five platform key/biometric tests and all four application/UI tests without skips. The final UI run used the assembled APK/test APK and `adb -s emulator-5580 shell am instrument -w cn.edu.ustc.dsh.mobile.test/androidx.test.runner.AndroidJUnitRunner`; it covered actual Hilt startup, missing-configuration denial, unsolicited callbacks, dark login, 2× text on a narrow layout and landscape registration controls. The default APK was also inspected to confirm the absence of `assets/deployment.json`. A configured→unconfigured build removed its previous asset, and an extra `client_secret` fixture was rejected before packaging. These fixture tests do not demonstrate real school login, complete foreground workflows, durable registration recovery, modern Android/physical hardware behavior or target-load readiness. The school configuration remains unavailable; development continues with local fixtures.
