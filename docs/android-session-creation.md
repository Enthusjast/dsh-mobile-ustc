# Android foreground session creation

The phone creates a new session in a currently authorized workspace using an explicitly advertised host preset. Creation is available from an allowed runtime or its session directory. It has its own foreground view and one authenticated Relay socket, with the same durable command coordinator used by chat. It does not require or manufacture a pre-existing session UUID, read subscription or local path.

`session.create_options.v1` is an additive metadata extension alongside `command.relay.v1` and `session.create.v1`. The current host publishes `session.create.options` and receives an acknowledgement; the phone requests `session.create.options.get` and receives `session.create.options.result` with the current runtime epoch. Metadata is held only by the live host connection and discarded on disconnect. It is not written to PostgreSQL. The service limits each snapshot to 128 workspaces and 128 ASCII preset tokens, public labels to 32 scalar characters/128 UTF-8 bytes, and total retained option bodies to 16 MiB. The host retries unacknowledged snapshots with a bounded jittered delay.

Workspace labels are explicit public configuration, with a short UUID fallback; they are never derived from `cwd` or the local workspace reference. Only uniquely mapped remote workspace IDs are offered. Preset names use the existing remote creation token grammar and the configured host allowlist; preset definitions, model credentials and paths remain on the host. Metadata shape or size incompatibility withholds this extension without changing the older Relay operations. The host still checks the exact workspace mapping and preset again before native creation.

The phone's creation ticket contains exactly `session.create` and `command.status`, authorized workspace UUIDs and no literal session IDs. Directory visibility, read permission or a session-only grant cannot grant creation. Relay revalidates the phone lease and host connection, intersects the published workspace list with the ticket's literal workspace scope, and binds the response to the request/runtime/epoch. The chooser accepts only that validated response. Grant changes, authentication loss and foreground/navigation disposal retire the view and queued sends.

The original creation intent contains its request/runtime IDs, workspace, preset and epoch. Its JCS digest matches the shared Go/TypeScript fixture. A local transaction saves it before dispatch eligibility; a second durable transaction marks the attempt uncertain before any socket write. An explicit same-ID retry first obtains current own-device REST status and is eligible only for `received`, with no proved host save and the same current epoch/options. Reconnection queries original status and fetches fresh options without automatically replaying attempted bodies. Status reconciliation remains available while the host cannot provide options.

Room schema version 3 makes the original session target nullable and adds workspace and separate created-session fields. Migrations from versions 1 and 2 preserve original intent bytes, request namespace, delivery facts, encrypted history and owner/key metadata. A settled creation stores the returned session UUID separately; it never overwrites the original workspace target or digest and never claims `agent_queued`. All operation types share the same request-ID namespace. Read-purpose cleanup preserves creation evidence still covered by `command.status` and its workspace scope; authoritative directory reconciliation removes creation rows outside those current scopes. Account exit retains the existing cryptographic erasure path.

The UI requires explicit current workspace/preset choices and keeps unsubmitted selections in ordinary memory. An unresolved earlier request requires an explicit decision before creating another request ID. Received-only retry preserves the original request; unknown or old-epoch requests cannot be forced through by changing their body. Creation success is shown only after authoritative settlement. Opening the result refreshes the directory and applies current read permission, rather than inserting an optimistic session entry. A stale dialog cannot silently target a new runtime epoch.

Validation is separated between shared JVM domain/TLS tests, actual npm DSH host metadata publication, Go socket authorization tests, encrypted legacy migrations, platform-key/controller/Compose fixtures, and the real Kotlin/Go/PostgreSQL/DSH composition. The combined SDK probe creates a native session from advertised options, reconciles its result, refuses settled replay, opens the current directory entry and continues the new session. These fixture scopes do not establish a complete physical APK-to-Go-to-DSH device run, school identity, production host provisioning, OS kill/power-loss behavior, target-scale acceptance or complete M1/M2 acceptance.

On 2026-10-25, all 109 shared JVM tests passed without failures/skips, Android check/lint and debug app/test APK builds passed, and the full API 26 application suite passed 62 tests. The 14 creation/controller/Compose/persistence cases also passed separately. Both real encrypted legacy migrations passed. Host contract/type/build verification passed all 173 tests, and the isolated PostgreSQL Go race plus actual Kotlin/DSH composition passed. The first long application run ended after the owned software emulator reported CPU-thread hangs and exited 139; the failing UI case passed alone, then the complete 62-case rerun passed on a fresh owned image with system transition animations disabled. This fixture recovery is not physical-device stability or performance acceptance.
