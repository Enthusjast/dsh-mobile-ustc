# 绑定确认的配对期限

五分钟配对码的期限约束待确认申请的手机确认和 Host 确认。服务端在锁定申请、主机、安装、
runtime、当前手机和组织成员后，使用 PostgreSQL `clock_timestamp()` 重新检查申请期限。
Host 确认还会等待原手机密钥检查；该等待结束后再次检查。事务开始时间或锁查询中提前计算
的过期布尔值都不能代表这些等待结束后的时间。

更新确认状态、写入审计及控制事件、创建初始 owner grants 后，提交前再复核一次期限。
此检查是确认的最终决策点；提交和网络响应可能随后完成，不以响应到达时间作为批准时间。
等待期间过期返回已有 HTTP 403 `access.denied`，不能激活 runtime 或留下本次确认、grants、
成功审计与状态变更事件。数据库查询失败仍返回服务不可用，不把数据库错误解释为到期。

初次期限检查发现已过期时，保留既有清理语义：将该申请设为 expired，撤销其 pending runtime，
并只在没有其他有效 runtime / installation 时撤销安装或 pending Host，保存到期审计与事件。
若在后续检查或审计等待期间才到期，则整体回滚本次尝试；之后的有效调用可以执行同一到期
清理。读状态的接口也会依据当前时间显示过期，不把回滚后保留的 pending 行解释为仍有效。

已批准申请的同参数确认重试是历史对账，不使用旧配对期限重新批准或撤权。它仍要求正确配对码、
当前账号/成员、目标未撤销，以及原来的手机证明或 Host 安装密钥和被核对用户。此路径不重复
创建 grants 或写入成功审计。新的同名登记仍须按[重新登记流程](installation-profile-management.md#撤销后重新登记)
创建新身份，并受新申请自己的期限约束。

本次不调整五分钟 TTL、HTTP 成功格式或数据库结构，也不增加自动重试确认。

## 验证

真实隔离 PostgreSQL 测试复现并覆盖七种等待跨过期限的情况：手机确认等待 runtime、手机密钥、
成员关系、确认审计；Host 确认等待原手机密钥、确认审计、初始 grant 审计。测试先确认真实
锁等待已经出现，再按数据库墙钟等待到期后释放锁；拒绝后核对没有新 grants 或成功确认审计。
另有正向用例验证已批准申请过期后的双端历史对账不重复写入。

正常链路另用 Go / PostgreSQL / 本机 npm DSH `0.2.1-rc.2` 双节点夹具验证。身份和模型为本地
夹具，未进行学校真实配置、Android APP、真机、大负载或厂商通道验收。
