# Android host binding

The foreground app now supports the phone side of installation/profile binding. It uses the configured school identity and registered device proof key; development and integration use local identity/model fixtures until school configuration is available. This does not complete M1 or M2 acceptance.

The user enters the computer's enrollment UUID and 256-bit URL-safe code. The app requests a read-only `POST /v1/enrollments/{id}/preview`, then displays organization, computer alias, profile, full installation-key thumbprint, configured opaque workspace references and expiry. The code is in the JSON body, never a URL, log, saved instance state or account checkpoint. The form uses ordinary Compose memory rather than saved state. Backgrounding, disposal, navigation, account changes and credential replacement retire an unsubmitted review and its private request handle.

The user explicitly checks the complete fingerprint/information and presses the confirmation button. The request handle is single-use and re-reads the preview before sending. Every immutable review fact is bound with the strict JCS representation; changed identity, key, profile, workspace, version or expiry requires another review. Only status/confirmation flags may change without invalidating those facts. Unsupported protocol versions, expiry, unknown fields, ambiguous workspace entries, different organizations and another account's confirmation cannot enable the action. These display facts do not authorize tool approvals or replace server authorization.

`POST /v1/enrollments/{id}/confirm` still requires the exact code, current membership and an active registered phone key. The independent host endpoint requires an allowlisted host OAuth client and the registered installation key. Host OAuth clients cannot register a phone or use phone-protected routes. This separation verifies client/key roles; it is not physical-phone attestation or a verified school device policy.

`GET /v1/enrollments/{id}` permits the initiating installation owner or confirming user. Phone reads require a registered device. Host reads additionally require the allowlisted host client and matching installation thumbprint. Another organization member needs an unexpired code in the preview request to inspect a pending application; preview alone neither confirms nor grants anything. Responses expose `installation_key_jkt` and the actor-relative `user_confirmed_by_me`, and never the code or installation private key. Expired preview capabilities are denied, while an authorized participant can still query historical status.

Confirmation results are checked against the reviewed identifiers and expiry, then resolved with a fresh actor-specific status read. A dropped/uncertain response retains only the public original ID for reconciliation and exposes a status-query action. Reconnect and foreground return issue reads, never an automatic confirmation retry. A resource-specific denial rechecks account authority instead of deleting an otherwise valid account. Old account/navigation generations cannot restore binding state after logout.

The UI distinguishes review, confirming, result unknown, waiting for the host, missing current access and ready. Phone confirmation alone does not mean completion. Even an approved enrollment is not a credential: the app looks up the current runtime directory, matching organization/host/runtime and valid access metadata before showing success. Granted actions still control subsequent session buttons and fresh service tickets. An approved historical enrollment cannot override current grant removal.

The service also gates API-created runtime eligibility on enrollment approval, including under a previously active host or shared installation. Pending, expired, denied and cancelled enrollments cannot acquire host credentials, attach/refresh a profile connection, appear through an early grant, obtain tickets, route scoped operations or retain a valid periodic connection lease. Legacy runtime rows with no enrollment represent explicit prior provisioning; normal creation always inserts its pending enrollment atomically. Migration 008 adds the partial eligibility index, without changing message storage or adding a new identity system.

Expiring one profile revokes that runtime and retires the installation/host only when no remaining usable resource needs them. It does not revoke an approved sibling or prevent another pending profile from finishing. A different phone account cannot claim someone else's confirmation through an idempotent approved retry. Existing audit/outbox writes and owner grants remain transactionally tied to the two confirmations; codes stay stored as digests.

The JVM tests exercise strict public models, review revalidation, one-use/cancellation behavior, uncertain-response reconciliation, foreground code retirement, independent host status and current directory access. PostgreSQL tests cover code/issuer/org isolation, actor attribution, expiry, shared profiles and runtime activation. The combined `npm run test:remote-kotlin` fixture runs the production Kotlin binding flow against TLS Go/PostgreSQL and a separate signed host HTTP client before the existing DSH content/command compositions. Native tests separately exercise actual Android keys/controller lifecycle and synthetic Compose state, including saved-state restoration of the form. Run Android fixture tests only on an explicitly provisioned owned device.

On 2026-10-25, all 78 shared JVM tests passed without skips, serialized Android lint/debug app/test-APK builds passed, and the explicit API 26 fixture suite passed all 34 tests. Five new controller/platform cases cover phone/host/directory sequencing, a lost confirmation reply across foreground changes, logout during a delayed preview, stale review/other-account denial and resource-specific denial without deleting the account. Five Compose cases cover full-fingerprint confirmation gating, secret exclusion from saved state, unknown-result query actions, public-ID-only recovery and a landscape/tablet layout at enlarged text scale. The small dark layout uses 340 dp width and 1.6 font scale; the light landscape/tablet simulation uses reduced density and 1.8 font scale. These simulations do not establish physical-tablet behavior.

The first native suite exposed a deterministic fixture shutdown lock conflict, rather than a binding assertion failure. The dispatcher called `MockWebServer.url()` while `shutdown()` held the server monitor and awaited dispatch queues. The fixture now caches its origin immediately after startup and cancels/closes its owned HTTP resources. The affected lost-response test then passed alone, followed by the complete 34-case suite. The owned software emulator was reprovisioned after a verified warm-boot GateKeeper loss/process exit, and no other device or system PostgreSQL instance was used.

Still required: real school OIDC/DPoP registration, a production host credential/key provider and local confirmation UI, organization-specific administrator policy, an Android APK-to-service-to-DSH device composition, physical target-device behavior and the remaining chat/approval/question/cache/file workflows. Pending binding secrets are intentionally not process-restored; a participant can re-enter the public application ID and query its current status. No production deployment or full milestone acceptance is inferred from fixture results.
