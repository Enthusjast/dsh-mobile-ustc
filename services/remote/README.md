# Remote service foundation

This Go service provides a strict resource-token authentication foundation, PostgreSQL-backed device registration/revocation, dual-confirmation host enrollment, grant-filtered directory reads, scoped realtime-ticket issuance, installation-key challenge exchange, a key-proved WebSocket handshake, and host-published session catalog metadata. The Relay routes scoped text submissions, command receipts, session snapshots/history and assistant streams. The host plugin includes a reconnecting WSS client and command journal adapter. Its ordinary CLI test uses a local protocol peer; `npm run test:remote-dsh` additionally runs this Go production entrypoint with isolated PostgreSQL and the npm DSH CLI. File handoff and production credential-provider integration remain open.

The service requires `REMOTE_ISSUER`, `REMOTE_AUDIENCE`, `REMOTE_JWKS_URL`, `REMOTE_CLIENT_IDS`, `REMOTE_REQUIRED_SCOPES`, `REMOTE_PUBLIC_ORIGIN`, and `REMOTE_DATABASE_URL`. `REMOTE_HOST_CLIENT_IDS` separately allowlists OAuth clients for host enrollment, confirmation, and host credential exchange; those clients must also appear in `REMOTE_CLIENT_IDS`. A development listener can use `REMOTE_LISTEN_ADDR=127.0.0.1:8080`. Start it with `go run ./cmd/remote` from this directory. `GET /healthz` is liveness-only; `GET /readyz` checks PostgreSQL. `GET /v1/me` requires a JWT access token, a DPoP proof and a provisioned active user. It returns the service `user_id` and current `memberships` resolved by the verified issuer/subject, alongside token identity and scopes. It is available before device enrollment, creates no authority and does not replace runtime grants; absent or suspended/deleted users receive 403 and database failure receives 503. `POST /v1/devices` registers separate approval and DPoP public keys, with the DPoP key bound to the access token; mobile directory, command-status, grant, ticket-issue, and revocation routes also require that key to belong to a non-revoked device. Host routes use the separate host-client allowlist and installation-key checks described below. Apply migrations `001_remote_control.up.sql` through `008_enrollment_activation_index.up.sql` in order before starting the service. Bind it to loopback during development. Production must place it behind a TLS ingress configured to the same external origin and use a PostgreSQL DSN with `sslmode=verify-full`.

Implemented routes are `GET /v1/devices/current`, `POST /v1/devices`, `DELETE /v1/devices/{id}`, `POST /v1/enrollments`, `GET /v1/enrollments/{id}`, `POST /v1/enrollments/{id}/confirm`, `POST /v1/enrollments/{id}/host-confirm`, `POST /v1/host-credentials/challenges`, `POST /v1/host-credentials`, `GET /v1/hosts`, `GET /v1/runtimes`, `GET /v1/runtimes/{id}/sessions`, `PUT /v1/runtimes/{id}/grants/{user_id}`, `DELETE /v1/runtimes/{id}/grants/{user_id}`, `POST /v1/realtime/tickets`, `GET /v1/realtime`, and `GET /v1/commands/{request_id}?device_id=...`. Host enrollment requires a DPoP-bound P-256 installation key and an OAuth client listed in `REMOTE_HOST_CLIENT_IDS`; phone confirmation requires an active registered device and organization membership, and host confirmation requires the installation key. Both confirmations atomically activate the host and issue owner grants to the host owner and confirming user. The API does not yet invoke a local desktop confirmation UI. Enrollment codes are random 256-bit values; only SHA-256 digests are stored. Device enrollment [reconciliation](../../docs/device-enrollment-recovery.md) queries only the current authenticated key and makes exact fresh-proof retries idempotent without reviving revoked keys. After activation, the installation owner can request a 90-second challenge and exchange a signed, one-use installation proof for an opaque five-minute connection credential. Challenge issuance is limited to four pending and 20 in five minutes per installation; no more than eight unexpired credentials can be active for one installation. Challenge and credential storage contain only SHA-256 digests; credential validation checks active host state, key version, expiry, and the registered key thumbprint. The WSS route validates mobile tickets or host credentials, consumes mobile tickets only after the registered-key proof succeeds, and registers the authenticated host runtime. Device sockets have a five-minute lease; host sockets expire with the host credential. It routes text-only queue/steer submissions to the current host runtime and accepts command receipts when both peers negotiate `command.relay.v1`. Both peers may additionally negotiate `session.cancel.v1` for epoch-bound cancellation with explicit `session.cancel` permission; [cancellation notes](../../docs/session-cancel-protocol.md) explain native acknowledgement, turn-end and durable retry semantics. Each submission rechecks the device key version, grant version, action, and session/workspace scope; PostgreSQL stores only request ID, session ID, state, and digest. Duplicate request IDs with matching content are idempotent; changed content conflicts. Host receipts advance the durable state machine and are audited. Message bodies remain in the mobile retry queue and host journal, not PostgreSQL. The bounded per-connection queue closes slow peers. Host session catalog snapshots and deltas update the metadata-only PostgreSQL directory; complete snapshots remove stale workspace mappings, and removed or disconnected sessions become unavailable. Session content routing requires the negotiated `session.read.v1` capability and explicit `session.read` in ticket and current grant. Every content frame rechecks the current host, device key, grant version and session/workspace scope. Subscriptions belong to one socket; history pages remain tied to the host sync and fixed cursor. Unsubscribe, connection loss and host replacement abort the follower. Projected payloads are fragmented within a 2 MiB logical limit. Both peers may negotiate `session.create.v1` for workspace-scoped creation before a session UUID exists. Creation and the existing session commands share durable request IDs and receipt handling; [creation notes](../../docs/session-create-protocol.md) describe workspace/preset limits, atomic settlement and epoch-bound retries. Peers may additionally negotiate `question.blocking.v1` for scoped blocking-question snapshots and epoch-bound answers, with explicit `question.answer` permission and durable command receipts; see [question protocol](../../docs/question-protocol.md). The separately negotiated `question.timed.v1` adds scoped native timed snapshots, subscription-bound claim/release and epoch-bound late answers; [timed-question notes](../../docs/timed-question-protocol.md) distinguish foreground settlement from durable late-message admission. The optional signed-approval server transport is described below; normal signed plugin wiring now has real CLI evidence. The foreground Kotlin command coordinator reconciles its device-bound status after reconnect without automatically resending an attempted body; see [Android command delivery](../../docs/android-command-delivery.md). The host plugin WSS client accepts an externally supplied credential/key signer; enrollment refresh and the OS key-store adapter are not part of that client. Ingress and application logs must redact Authorization on this route. Runtime owners can delegate only actions and resources within their existing grant; owner grants must include `grant.manage`, and organization admins can assign them. Grant changes increment the version and write audit and outbox records in the same transaction. Realtime tickets last 30 seconds, store only a SHA-256 digest, and are atomically consumed by the service store after rechecking current device, membership, runtime, and grant version. Mobile and host handshakes require a fresh signature by the registered key; the current WSS capability set includes heartbeat, text message submission, session creation/cancellation, blocking/timed questions, host session catalog synchronization and scoped session reads. Directory and command-status data are filtered by the active user, organization membership, runtime grant, action scope, and session or workspace scope. An empty scope array grants no access. The OpenAPI contract is in `../../contracts/openapi/remote.yaml`; WSS frame schemas and golden examples are in `../../contracts/ws/v1`.

Access tokens must be signed with RS256 or ES256, typed as `at+jwt`, issued by the configured issuer, intended for the configured audience, minted to an allowed OAuth client, contain every configured scope, and bind a P-256 proof key through `cnf.jkt`. No caller may choose the JWKS URL, algorithm, audience, client allowlist, or public origin through a request.

Resource requests must use `Authorization: DPoP <access-token>` and a separate `DPoP` proof JWT. The resource service challenges for a one-time `DPoP-Nonce`, verifies the method, public URI, `ath`, proof-key thumbprint, timestamp and `jti`, and rejects replay. Its in-memory nonce store supports a single service process only; multi-node deployment needs a shared atomic replay store before it can pass M1.

The module requires Go 1.26.0 or later; development verification used Go 1.26.10. PostgreSQL connections use the `pgx` database/sql driver pinned in `go.mod`:

```sh
go test -race -count=1 ./...
go build -o /tmp/dsh-remote ./cmd/remote
```

The PostgreSQL integration test is opt-in because it creates and drops a uniquely named database. Set `REMOTE_TEST_DATABASE_URL` to a local PostgreSQL admin DSN whose role can create databases, then run `go test ./internal/store -run TestPostgresMigrationGrantLifecycleAndTransactionalOutbox`. It applies all ordered migrations through 008 and exercises grant writes, scope denial, enrollment idempotency and dual confirmation, atomic ticket consumption, installation challenge consumption and digest storage, host credential key binding, realtime ticket key-version binding, runtime connection attach/touch/detach, session catalog snapshots/deltas and scoped directory reads, command ID conflict/idempotency and receipt transitions, stale grant-version rejection, audit/outbox atomicity, and device revocation in that temporary database.

The migrations are a schema baseline only; this repository does not yet apply them automatically. Migration 002 refuses to proceed if enrollment rows already exist, so reconcile those rows before applying it to a populated deployment. Migrations 001–008 and the repository integration suite passed against an isolated PostgreSQL 18.6 cluster using a private Unix socket; the existing system cluster was not modified. The repository suite verifies database behavior; the separate combined Go/DSH fixture test below verifies the Relay chain. Neither establishes deployed school identity. Production user/org provisioning, local host confirmation/key provisioning, real-school OIDC/PKCE acceptance, a shared replay store, Android persistent transcript caching, remaining signed-approval capability/platform coverage, Android timed-question UI and mobile lease renewal, durable multi-node revoke fanout and target-load/failure-window measurements remain outstanding. The entrypoint now runs single-process outbox invalidation and independent batch connection checks; see [revocation propagation](../../docs/revocation-propagation.md). The authentication contract and its remaining gates are recorded in [M1 authentication notes](../../docs/m1-authentication.md).

Session subscription identities, fragment limits and verification boundaries are documented in [session read protocol](../../docs/session-read-protocol.md). Existing grants do not gain body access from `session.list`; explicitly add `session.read` when authorized. Current per-frame authorization uses PostgreSQL checks; the target streaming load and multi-node routing are not yet validated.

Runtime directory rows include the authenticated user's organization and current grant scope/version; session rows include their opaque workspace UUID (or null). These metadata snapshots support permission-aware mobile controls and explicit ticket-scope selection. They never replace fresh ticket/resource authorization or expose native IDs, paths or content.

The [combined Go/DSH test](../../docs/go-dsh-integration.md) passed with local signed identity/model fixtures, covering enrollment, key proofs, text commands, streamed reads, pagination, idempotency, database content boundaries and grant revocation. It creates its own socket-only PostgreSQL cluster and does not touch the system cluster.

The [binding review/activation protocol](../../docs/host-binding-protocol.md) adds a code-protected phone preview, actor-relative confirmation status and key-bound host status. Host OAuth clients cannot register or impersonate phone clients on protected routes. New profiles remain unavailable until both confirmations, even under an existing active installation or early grant. Expiry preserves sibling profiles; apply migration 008 for the partial eligibility index. The production host confirmation UI, key provider and school policy remain gates.

`npm run test:remote-kotlin` additionally compiles the SDK-free JVM probe and runs the production Kotlin reader against real TLS Go/PostgreSQL and npm DSH. It verifies signed-token revalidation, scoped directory access, DPoP ticket/proof/heartbeat, offline correlation, large Unicode snapshots, fixed history, live settlement and fresh-snapshot reopen, plus Kotlin queue submission/native observation, own-device status, admitted-ID replay denial and epoch-bound native interruption before the separate command chain. JDK 17/21 and Gradle dependencies are required; the ordinary runner remains independent of Java. See [Android read evidence and its remaining device/production gates](../../docs/android-realtime.md).

Set `REMOTE_APPROVAL_POLICY_FILE` to explicitly enable the server's signed-approval extension and `POST /v1/approvals/{id}/decisions`. The [approval protocol](../../docs/approval-protocol.md) specifies the verified assurance mapping, protected service-key file, independently provisioned host trust anchor, transient details RPC, bounded fragments, fresh HTTPS admission, scoped WSS forwarding and metadata/result reconciliation. Both the capability and endpoint remain unavailable without this configuration. Server transport and PostgreSQL/JWT/DPoP integration are tested; the normal DSH plugin's signed callback/body/guard lifecycle and durable delivery now have real Bash/CLI coverage. Android, production key provisioning and the remaining capability/platform gates remain open.
