# Remote service foundation

This Go service provides a strict resource-token authentication foundation, PostgreSQL-backed device registration/revocation, dual-confirmation host enrollment, grant-filtered directory reads, scoped realtime-ticket issuance, installation-key challenge exchange, and a key-proved WebSocket handshake. The Relay routes scoped text submissions and command receipts. The host plugin now includes a reconnecting WSS client and command journal adapter; its DSH CLI integration currently uses a local protocol peer, not this Go service. Session synchronization, file handoff, and production credential-provider integration remain open.

The service requires `REMOTE_ISSUER`, `REMOTE_AUDIENCE`, `REMOTE_JWKS_URL`, `REMOTE_CLIENT_IDS`, `REMOTE_REQUIRED_SCOPES`, `REMOTE_PUBLIC_ORIGIN`, and `REMOTE_DATABASE_URL`. `REMOTE_HOST_CLIENT_IDS` separately allowlists OAuth clients for host enrollment, confirmation, and host credential exchange; those clients must also appear in `REMOTE_CLIENT_IDS`. A development listener can use `REMOTE_LISTEN_ADDR=127.0.0.1:8080`. Start it with `go run ./cmd/remote` from this directory. `GET /healthz` is liveness-only; `GET /readyz` checks PostgreSQL. `GET /v1/me` requires a JWT access token and a DPoP proof. `POST /v1/devices` registers separate approval and DPoP public keys, with the DPoP key bound to the access token; mobile directory, command-status, grant, ticket-issue, and revocation routes also require that key to belong to a non-revoked device. Host routes use the separate host-client allowlist and installation-key checks described below. Apply migrations `001_remote_control.up.sql` through `004_realtime_handshake.up.sql` in order before starting the service. Bind it to loopback during development. Production must place it behind a TLS ingress configured to the same external origin and use a PostgreSQL DSN with `sslmode=verify-full`.

Implemented routes are `POST /v1/devices`, `DELETE /v1/devices/{id}`, `POST /v1/enrollments`, `GET /v1/enrollments/{id}`, `POST /v1/enrollments/{id}/confirm`, `POST /v1/enrollments/{id}/host-confirm`, `POST /v1/host-credentials/challenges`, `POST /v1/host-credentials`, `GET /v1/hosts`, `GET /v1/runtimes`, `GET /v1/runtimes/{id}/sessions`, `PUT /v1/runtimes/{id}/grants/{user_id}`, `DELETE /v1/runtimes/{id}/grants/{user_id}`, `POST /v1/realtime/tickets`, `GET /v1/realtime`, and `GET /v1/commands/{request_id}?device_id=...`. Host enrollment requires a DPoP-bound P-256 installation key and an OAuth client listed in `REMOTE_HOST_CLIENT_IDS`; phone confirmation requires an active registered device and organization membership, and host confirmation requires the installation key. Both confirmations atomically activate the host and issue owner grants to the host owner and confirming user. The API does not yet invoke a local desktop confirmation UI. Enrollment codes are random 256-bit values; only SHA-256 digests are stored. After activation, the installation owner can request a 90-second challenge and exchange a signed, one-use installation proof for an opaque five-minute connection credential. Challenge issuance is limited to four pending and 20 in five minutes per installation; no more than eight unexpired credentials can be active for one installation. Challenge and credential storage contain only SHA-256 digests; credential validation checks active host state, key version, expiry, and the registered key thumbprint. The WSS route validates mobile tickets or host credentials, consumes mobile tickets only after the registered-key proof succeeds, and registers the authenticated host runtime. Device sockets have a five-minute lease; host sockets expire with the host credential. It routes text-only queue/steer submissions to the current host runtime and accepts command receipts when both peers negotiate `command.relay.v1`. Each submission rechecks the device key version, grant version, action, and session/workspace scope; PostgreSQL stores only request ID, session ID, state, and digest. Duplicate request IDs with matching content are idempotent; changed content conflicts. Host receipts advance the durable state machine and are audited. Message bodies remain in the mobile retry queue and host journal, not PostgreSQL. The bounded per-connection queue closes slow peers. Session synchronization, streaming, approval/question frames, and reconnect status reconciliation remain open. The host plugin WSS client accepts an externally supplied credential/key signer; enrollment refresh and the OS key-store adapter are not part of that client. Ingress and application logs must redact Authorization on this route. Runtime owners can delegate only actions and resources within their existing grant; owner grants must include `grant.manage`, and organization admins can assign them. Grant changes increment the version and write audit and outbox records in the same transaction. Realtime tickets last 30 seconds, store only a SHA-256 digest, and are atomically consumed by the service store after rechecking current device, membership, runtime, and grant version. Mobile and host handshakes require a fresh signature by the registered key; the current WSS capability set includes heartbeat and text message submission. Directory and command-status data are filtered by the active user, organization membership, runtime grant, action scope, and session or workspace scope. An empty scope array grants no access. The OpenAPI contract is in `../../contracts/openapi/remote.yaml`; WSS frame schemas and golden examples are in `../../contracts/ws/v1`.

Access tokens must be signed with RS256 or ES256, typed as `at+jwt`, issued by the configured issuer, intended for the configured audience, minted to an allowed OAuth client, contain every configured scope, and bind a P-256 proof key through `cnf.jkt`. No caller may choose the JWKS URL, algorithm, audience, client allowlist, or public origin through a request.

Resource requests must use `Authorization: DPoP <access-token>` and a separate `DPoP` proof JWT. The resource service challenges for a one-time `DPoP-Nonce`, verifies the method, public URI, `ath`, proof-key thumbprint, timestamp and `jti`, and rejects replay. Its in-memory nonce store supports a single service process only; multi-node deployment needs a shared atomic replay store before it can pass M1.

Development verification uses the Go 1.26.0 version pinned in go.mod. PostgreSQL connections use the `pgx` database/sql driver pinned in `go.mod`:

```sh
go test -race ./...
go build -o /tmp/dsh-remote ./cmd/remote
```

The PostgreSQL integration test is opt-in because it creates and drops a uniquely named database. Set `REMOTE_TEST_DATABASE_URL` to a local PostgreSQL admin DSN whose role can create databases, then run `go test ./internal/store -run TestPostgresMigrationGrantLifecycleAndTransactionalOutbox`. It applies migrations 001 through 004 and exercises grant writes, scope denial, enrollment idempotency and dual confirmation, atomic ticket consumption, installation challenge consumption and digest storage, host credential key binding, realtime ticket key-version binding, runtime connection attach/touch/detach, command ID conflict/idempotency and receipt transitions, stale grant-version rejection, audit/outbox atomicity, and device revocation in that temporary database.

The migrations are a schema baseline only; this repository does not yet apply them automatically. Migration 002 refuses to proceed if enrollment rows already exist, so reconcile those rows before applying it to a populated deployment. Repository SQL has not been exercised against a live PostgreSQL server. User/org provisioning, wiring explicit local confirmation, the OIDC/PKCE client flow, a shared replay store, session snapshot/subscription and assistant-stream routing, approval/question forwarding, mobile lease renewal, and revoke propagation over active sockets remain outstanding. The authentication contract and its remaining gates are recorded in [M1 authentication notes](../../docs/m1-authentication.md).
